## 배포 명령은 누가 실행할까?

쿠버네티스 YAML은 어느 정도 읽을 수 있게 됐다. 그러면 이 YAML은 누가 클러스터에 넣을까?

나는 당연히 CI가 넣는다고 생각했다. 머지하면 파이프라인이 돌면서 배포 명령을 실행하는 그림이다. 프론트엔드 배포가 대체로 그렇게 돌아가니까.

그런데 저장소 어디를 봐도 워크로드를 배포하는 명령이 없었다. 대신 Git 저장소 주소와 폴더 경로를 적어 둔 파일이 있었다. 이게 GitOps라는 방식이었다.

## 클러스터가 Git을 읽으러 온다

GitOps에서는 방향이 반대다. CI가 클러스터에 밀어 넣는 게 아니라, 클러스터 안에서 도는 프로그램이 Git을 읽으러 온다.

```text
내가 생각한 방식
  CI ──(배포 명령)──▶ 클러스터

GitOps
  클러스터 안의 프로그램 ──(주기적으로 읽음)──▶ Git
```

이 프로그램이 Argo CD다. 하는 일은 단순하다. Git에 적힌 내용과 클러스터의 지금 상태를 계속 비교하고, 다르면 Git 쪽으로 맞춘다.

인프라 코드와 같은 구조인데 차이가 하나 있다. 인프라 코드는 명령을 실행할 때 한 번 비교했다. Argo CD는 계속 돌면서 비교한다.

그래서 이 방식에서 배포는 **Git에 커밋하는 일**이 된다. 커밋이 main에 들어가면 나머지는 Argo CD가 한다.

## 무엇을 읽을지는 어디에 적혀 있을까?

저장소에서 본 그 파일이 Application이라는 리소스였다.

```yaml
# 설명용으로 줄인 예시
kind: Application
metadata:
  name: shop-api-dev
spec:
  source:
    repoURL: https://github.com/example/deploy.git
    targetRevision: main
    path: charts/web-service
    helm:
      valueFiles:
        - apps/dev/shop-api/values.yaml
        - apps/dev/shop-api/release.yaml
  destination:
    namespace: shop-dev
```

읽어보면 이렇다. 이 저장소의 main 브랜치에서, 이 chart를, 이 값 파일 두 개로 채워서, `shop-dev`에 유지해라.

chart와 values 파일 두 개가 여기서 만난다. 파일 하나에 "무엇을 어디에"가 다 적혀 있어서, 서비스 하나가 어떻게 배포되는지 알고 싶을 때는 이 파일부터 읽으면 됐다.

## 누가 직접 고치면 어떻게 될까?

Application에는 이런 설정도 있었다.

```yaml
syncPolicy:
  automated:
    prune: true
    selfHeal: true
```

- `automated`: Git이 바뀌면 사람이 누르지 않아도 반영한다
- `prune`: Git에서 지운 것은 클러스터에서도 지운다
- `selfHeal`: 누가 클러스터를 직접 고치면 Git 상태로 되돌린다

`selfHeal`이 재미있었다. 급해서 클러스터에 들어가 replica 수를 직접 바꿨다고 해보자. 조금 지나면 Argo CD가 Git에 적힌 값으로 되돌려 놓는다.

처음에는 불편하겠다고 생각했다. 그런데 반대로 보면, 이게 켜져 있어야 "지금 떠 있는 것은 Git에 적힌 그대로다"라고 말할 수 있다. 누가 몰래 바꾼 설정이 남아 있을 수 없으니까.

서버 상태를 유일한 기준으로 두고 화면은 그걸 따라가게 만드는 것과 비슷하다고 느꼈다. 기준이 하나여야 어긋났을 때 어느 쪽이 맞는지 고민하지 않는다.

## 기준이 Git이면 무엇이 좋을까?

정리하면서 장점이 익숙한 것들이라는 걸 알았다.

- 무엇이 배포돼 있는지 궁금하면 main 브랜치를 보면 된다.
- 누가 언제 무엇을 바꿨는지는 커밋 이력에 있다.
- 되돌리고 싶으면 커밋을 revert한다.
- 바꾸기 전에 PR로 리뷰한다.

전부 코드를 다루면서 하던 일이다. 인프라를 위해 새 절차를 배우는 게 아니라 이미 쓰던 절차를 그대로 쓴다.

보안 쪽 이점도 있었다. CI가 배포 명령을 실행하려면 클러스터에 접근할 권한을 들고 있어야 한다. GitOps에서는 CI가 Git에 커밋만 하면 되니 그 권한이 필요 없다.

## 환경은 왜 브랜치가 아니라 폴더일까?

공부하는 내내 걸렸던 부분이다. 나는 dev 브랜치는 개발 환경, main 브랜치는 운영 환경일 거라고 생각했다. 그런데 저장소에는 브랜치가 main 하나뿐이었고, 환경은 폴더로 나뉘어 있었다.

```text
apps/
  dev/
    shop-api/
      values.yaml
      release.yaml
  prod/
    shop-api/
      values.yaml
      release.yaml
```

왜 그럴까? 애플리케이션 코드는 dev에서 확인한 코드가 그대로 main으로 가니까 브랜치로 나눠도 문제가 없다. 그런데 배포 설정은 환경마다 **값이 원래 달라야** 한다.

```text
dev:   replica 1, 작은 DB
prod:  replica 3, 큰 DB
```

브랜치로 나누면 dev에서 main으로 머지할 때마다 "달라야 하는 값"과 "옮겨야 하는 변경"을 사람이 골라내야 한다. 머지할 때마다 충돌이 나는 모습이 그려졌다.

폴더로 나누면 이 문제가 없다. main 하나에 모든 환경의 현재 상태가 있고, dev와 prod가 어떻게 다른지는 두 파일을 비교하면 보인다. dev에서 prod로 옮기는 건 머지가 아니라 값을 복사하는 변경이 된다.

폴더로 나눠 두면 얻는 게 하나 더 있었다. 경로만 보고 규칙을 걸 수 있다. `apps/prod/` 아래가 바뀌면 승인자가 필요하다는 식이다.

## 그러면 인프라 코드는 누가 적용할까?

여기서 인프라 코드와 연결이 됐다. 설정 저장소에는 도구가 둘 있었고 맡은 일이 달랐다.

| 대상                                      | 누가    | 언제                           |
| ----------------------------------------- | ------- | ------------------------------ |
| 네트워크, DB, 클러스터 같은 클라우드 자원 | Pulumi  | PR에서 미리 보고, 머지 후 적용 |
| 클러스터 위에 올라가는 서비스             | Argo CD | 계속 Git을 보면서              |

설정이 "실행할 곳을 준비하는 것"과 "그 위에 무엇을 띄울지 정하는 것"으로 나뉜다고 봤는데, 그게 도구로도 나뉘어 있던 것이다. 저장소의 최상위 폴더가 둘로 갈라져 있던 이유도 이거였다.

## 마치며

이번 글을 정리하면서 배포를 보는 눈이 꽤 바뀌었다. 배포를 명령을 실행하는 일로만 생각했는데, GitOps에서는 Git에 원하는 상태를 적는 일이었다. 실행은 클러스터가 알아서 한다.

아직 궁금한 것도 남았다. Argo CD가 맞추다가 실패하면 어떻게 되는지, 서비스 여러 개가 서로 순서를 지켜야 할 때는 어떻게 하는지. 순서를 숫자로 정하는 기능이 있다는 정도만 확인했고 자세히는 보지 못했다.
