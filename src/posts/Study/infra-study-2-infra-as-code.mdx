## 서버를 만드는 코드가 TypeScript였다

배포 설정 저장소의 내용은 크게 두 종류였다. 실행할 곳을 준비하는 설정과, 그 위에 무엇을 띄울지 정하는 설정. 이번 글은 앞쪽을 정리한다.

클라우드에 데이터베이스를 하나 만든다고 하면 나는 콘솔 화면에서 버튼을 누르는 모습을 떠올렸다. 그런데 저장소를 열어보니 이런 코드가 있었다.

```ts
// 설명용으로 줄인 예시
const db = new aws.rds.Instance("main-db", {
  instanceClass: "db.t4g.micro",
  allocatedStorage: 20,
});
```

익숙한 TypeScript인데 하는 일이 낯설었다. 이 코드를 실행하면 데이터베이스가 생긴다는 걸까? 이런 방식을 IaC(Infrastructure as Code)라고 부른다는 것부터 찾아봤다.

## 콘솔에서 클릭하면 안 되는 이유가 있을까?

혼자 쓰는 작은 서비스라면 콘솔로도 충분하다고 생각한다. 문제는 여럿이 오래 운영할 때 생긴다.

- 같은 구성을 다른 환경에 한 번 더 만들어야 할 때, 어떤 버튼을 눌렀는지 기억해야 한다.
- 누가 언제 왜 설정을 바꿨는지 남지 않는다.
- 바꾸기 전에 무엇이 달라질지 미리 볼 방법이 없다.

코드로 적어 두면 이 문제들이 익숙한 방식으로 풀린다. 다른 환경에는 같은 코드를 다시 적용하면 되고, 변경 이력은 Git에 남고, 변경 전에는 PR에서 리뷰한다.

프론트엔드 코드를 다루던 방식이 그대로 인프라에 적용된다는 점이 처음에는 좀 신기했다.

## new를 썼는데 왜 바로 만들어지지 않을까?

위 코드에서 가장 헷갈린 건 `new`였다. 이 줄이 실행되는 순간 데이터베이스가 만들어진다고 읽었는데, 그렇지 않았다.

이 코드는 "만들어라"가 아니라 **"이런 것이 있어야 한다"** 는 뜻이다. 도구가 코드를 읽어서 있어야 할 것의 목록을 만들고, 지금 실제로 있는 것과 비교한 다음, 다른 부분만 고친다.

```text
코드에 적힌 것        지금 실제로 있는 것
main-db (micro)  vs  main-db (micro)   → 같다. 아무것도 안 한다
cache            vs  (없음)             → 새로 만든다
```

그래서 같은 코드를 여러 번 적용해도 결과가 같다. 이미 그 상태라면 아무 일도 일어나지 않는다.

이 구조를 이해하고 나서 떠오른 게 React였다.

```tsx
<button className={on ? "active" : ""}>{on ? "켜짐" : "꺼짐"}</button>
```

React에서도 "버튼에 클래스를 추가해라"라고 쓰지 않는다. 지금 상태에서 화면이 어떤 모양이어야 하는지만 적으면, React가 이전 화면과 비교해서 달라진 부분만 DOM에 반영한다.

인프라 코드도 같은 방식이었다. 결과를 적어 두면 차이는 도구가 계산한다. 이런 방식을 선언형이라고 부르는데, 매일 쓰던 개념이라 여기서부터는 이해가 빨랐다.

## 적용하기 전에 미리 볼 수 있다

차이를 계산한다는 건 적용하기 전에 그 차이를 보여줄 수도 있다는 뜻이다. 이 저장소에서 쓰는 도구는 Pulumi였는데, 명령이 둘로 나뉘어 있었다.

```bash
pulumi preview   # 무엇이 바뀔지 보여주기만 한다
pulumi up        # 실제로 적용한다
```

preview 결과는 이런 식으로 나온다.

```text
  + cache      create    새로 만든다
  ~ main-db    update    설정만 바꾼다
 +- old-db     replace   지우고 새로 만든다
```

여기서 하나 놀랐던 게 `replace`다. 어떤 설정은 있는 것을 고칠 수 없어서 지우고 새로 만든다고 한다. 서버라면 다시 띄우면 되지만 데이터베이스라면 안에 든 데이터가 같이 사라진다.

코드 리뷰에서 diff를 읽는 것처럼 인프라 변경에서는 이 preview를 읽는다. PR을 열면 preview가 자동으로 돌아서 결과를 보여주게 해 두는 것도 그래서였다. 한 줄 고쳤을 뿐인데 `replace`가 뜨면 멈추고 다시 봐야 한다.

## 도구는 자기가 만든 것을 어떻게 기억할까?

공부하다가 막힌 부분이 하나 더 있었다. 코드에서 어떤 자원을 지우면 도구가 실제 자원도 지운다. 그런데 코드에는 이미 없는데, 그게 원래 있었다는 걸 어떻게 알까?

도구가 따로 장부를 들고 있었다. 자기가 만든 자원의 목록과 실제 ID를 기록해 둔 것으로, **state**라고 부른다.

```text
코드에 적힌 이름      실제로 만들어진 것
main-db          →   db-7f3a9c1
```

그래서 비교 대상은 사실 셋이다. 코드, 장부, 실제. 장부가 실제와 어긋나면 도구가 잘못 판단할 수 있어서, 이 장부는 팀이 함께 쓰는 곳에 두고 동시에 두 사람이 적용하지 못하게 잠근다고 한다.

누군가 콘솔에서 설정을 직접 바꾸면 코드와 실제가 어긋난다. 이걸 drift라고 부르는데, 코드로 관리하는 자원은 콘솔에서 손대지 않는다는 규칙이 왜 있는지 이걸 보고 이해했다.

## 같은 코드를 dev와 prod에 쓰려면?

dev와 prod에 같은 구성이 필요하다면 코드를 복사해야 할까? 그렇지는 않았다. 코드는 하나로 두고 환경마다 달라지는 값만 따로 뺀다.

```yaml
# dev 환경의 값
config:
  database:
    instanceClass: db.t4g.micro
```

```yaml
# prod 환경의 값
config:
  database:
    instanceClass: db.r6g.large
```

Pulumi에서는 이렇게 같은 코드에 값만 다르게 적용한 단위를 **stack**이라고 부른다. 저장소에서 계속 보이던 그 단어였다. stack마다 장부도 따로 가진다.

`.env.development`와 `.env.production`을 나눠 쓰는 것과 비슷하게 읽으면 됐다.

다만 이 값 파일은 Git에 올라간다. 비밀번호 같은 값을 그대로 적으면 안 되는데, 도구가 값을 암호화해서 저장하는 기능을 제공하고 있었다. 파일에는 암호문만 남고, 풀 수 있는 열쇠는 클라우드 쪽에 둔다.

## 마치며

정리하면서 가장 크게 바뀐 건 인프라 코드를 읽는 방식이다. 위에서 아래로 실행되는 스크립트로 읽으면 이해가 안 됐는데, "있어야 할 것의 목록"으로 읽으니 React 컴포넌트를 읽는 것과 크게 다르지 않았다.

아직 모르는 것도 많다. 자원 하나하나가 무슨 일을 하는지는 클라우드를 따로 공부해야 알 수 있고, `replace`가 어떤 설정에서 일어나는지도 자원마다 다르다고 한다. 지금은 코드의 모양과 적용되는 방식을 이해한 정도다.
