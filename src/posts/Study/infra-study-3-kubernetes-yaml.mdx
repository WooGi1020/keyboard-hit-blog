## 쿠버네티스는 어디까지 알아야 할까?

쿠버네티스라는 이름은 많이 들었지만 공부할 엄두는 내지 못했다. 책 한 권 분량이라는 말을 들었고, 프론트엔드 개발자가 거기까지 알아야 하나 싶었다.

그런데 설정 저장소를 읽는 게 목적이라면 범위가 꽤 좁아진다. 클러스터를 설치하고 운영하는 법은 몰라도 된다. **YAML 파일 하나가 무엇을 정하는지**만 읽을 수 있으면 됐다.

이번 글은 그 정도 깊이로만 정리한다.

## 컨테이너를 띄워주는 플랫폼이다

이미지를 실행한 것이 컨테이너다. 컨테이너 하나를 띄우는 건 명령 한 줄이면 된다. 문제는 여러 개를 계속 띄워 둬야 할 때다.

- 컨테이너가 죽으면 누가 다시 띄울까?
- 세 개를 띄웠는데 요청은 어디로 보내야 할까?
- 새 버전으로 바꿀 때 끊기지 않게 하려면?

쿠버네티스는 이런 일을 맡아주는 플랫폼이다. 서버 여러 대를 묶어 놓은 것을 **클러스터**라고 하고, 그 위에 컨테이너를 올린다.

쓰는 방식은 인프라 코드와 같았다. "컨테이너 세 개가 떠 있어야 한다"고 적어 두면 쿠버네티스가 그 상태를 유지한다. 하나가 죽으면 다시 띄운다. 또 선언형이다.

## Deployment: 무엇을 몇 개 띄울지

쿠버네티스에서는 적어 두는 대상을 리소스라고 부르고, 종류가 `kind`에 적혀 있다. 가장 많이 본 건 Deployment였다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop-api
spec:
  replicas: 3
  template:
    spec:
      containers:
        - name: shop-api
          image: registry.example.com/shop-api:1.4.0
          ports:
            - containerPort: 8080
```

처음에는 줄이 많아서 겁이 났는데, 실제로 읽어야 할 건 세 군데였다.

- `replicas: 3` — 세 개를 띄운다
- `image` — 이 이미지를 쓴다
- `containerPort` — 이 포트로 요청을 받는다

나머지는 대부분 정해진 형식이다. 배포는 결국 어떤 이미지를 어디에 어떤 설정으로 실행할지 정하는 일인데, 그게 그대로 이 파일에 적혀 있었다.

## Service: 세 개 중 어디로 요청을 보낼까?

컨테이너는 죽고 다시 뜰 때마다 주소가 바뀐다. 세 개가 떠 있으면 주소도 세 개다. 호출하는 쪽에서 이걸 일일이 알 수는 없다.

Service는 그 앞에 고정된 이름 하나를 붙여준다.

```text
호출하는 쪽 ─▶ shop-api (Service) ─┬▶ 컨테이너 1
                                  ├▶ 컨테이너 2
                                  └▶ 컨테이너 3
```

다른 서버는 `shop-api`라는 이름으로만 호출하면 되고, 뒤에서 어느 컨테이너가 받는지는 신경 쓰지 않는다. 로드 밸런서를 떠올리면 비슷하다.

## 설정값은 어디에 둘까?

프론트엔드에서 환경변수를 `.env`에 두듯 쿠버네티스에도 설정을 따로 두는 리소스가 있다.

- **ConfigMap**: 비밀이 아닌 설정
- **Secret**: 비밀번호나 키 같은 값

Deployment에서 이 둘을 가리키면 컨테이너에 환경변수로 들어간다. 코드와 설정을 분리한다는 익숙한 원칙이다.

하나 더 있다. **Namespace**는 리소스를 묶는 폴더 같은 것이다. 같은 클러스터 안에 `shop-dev`와 `shop-prod`를 나눠 두면 이름이 같은 리소스도 서로 겹치지 않는다.

여기까지 다섯 개가 내가 저장소에서 계속 마주친 리소스다. Deployment, Service, ConfigMap, Secret, Namespace.

## 서비스가 열 개면 YAML도 열 벌일까?

리소스를 이해하고 나서 생긴 의문이다. 서비스마다 Deployment와 Service가 필요한데, 내용은 이름과 이미지만 빼면 거의 같다. 열 개를 복사해서 관리하는 걸까?

여기서 **Helm**이 나온다. YAML에 빈칸을 뚫어 두고 값만 바꿔 끼우는 도구다.

```yaml
# 템플릿: 빈칸이 뚫린 YAML
spec:
  replicas: { { .Values.replicas } }
  template:
    spec:
      containers:
        - name: { { .Values.name } }
          image: { { .Values.image } }
```

```yaml
# values.yaml: 빈칸에 들어갈 값
name: shop-api
replicas: 3
image: registry.example.com/shop-api:1.4.0
```

템플릿 묶음을 **chart**, 값을 **values**라고 부른다. 저장소에서 계속 보이던 단어 둘이 여기서 풀렸다.

이건 컴포넌트와 props로 읽으니 바로 이해됐다. 공용 chart 하나가 컴포넌트이고, 서비스마다 가진 values 파일이 props다. 서비스가 늘어도 values 파일만 하나 더 생긴다.

```text
charts/
  web-service/          공용 템플릿 (컴포넌트)
apps/
  shop-api/values.yaml  이 서비스의 값 (props)
  cart-api/values.yaml
```

## values 파일이 왜 두 개일까?

저장소를 보면서 이상했던 점이 하나 있었다. 한 서비스 폴더 안에 값 파일이 두 개씩 있었다.

```text
values.yaml    replica 수, 환경변수, 포트
release.yaml   이미지 버전
```

Helm은 값 파일을 여러 개 받아서 합칠 수 있다. 그런데 왜 굳이 나눴을까?

두 파일은 바뀌는 이유와 빈도가 달랐다. replica 수나 환경변수는 사람이 가끔 고친다. 이미지 버전은 배포할 때마다 바뀐다. 한 파일에 두면 Git 이력에서 설정 변경과 버전 배포가 뒤섞인다.

나눠 두면 "이 서비스의 설정이 언제 바뀌었나"와 "언제 어떤 버전이 배포됐나"를 따로 볼 수 있다. 자주 바뀌는 상태와 잘 안 바뀌는 상태를 분리하는 건 프론트엔드에서도 하던 일이라 납득이 갔다.

## 마치며

쿠버네티스 전체로 보면 이번에 정리한 건 아주 작은 부분이다. 네트워크가 어떻게 연결되는지, 컨테이너가 서버에 어떻게 배치되는지 같은 건 하나도 다루지 않았다.

그래도 목적에는 충분했다. 이제 YAML을 열면 `kind`부터 보고, Deployment면 이미지와 개수를, values 파일이면 어느 chart에 들어가는 값인지를 찾아 읽는다.

참고로 `helm template`이라는 명령을 쓰면 템플릿에 값을 끼운 최종 YAML을 클러스터 없이도 뽑아볼 수 있다. 빈칸이 채워진 결과를 눈으로 확인할 수 있어서, 구조가 헷갈릴 때 써보려고 한다.
