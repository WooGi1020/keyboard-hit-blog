# 🧯 `{ once: true }` 를 걸었는데 왜 리스너가 남아 있을까?

---

## 🔗 들어가며

### ✨ 스트림 유틸의 자원 정리를 점검하다 만난 것

- 최근 실시간 스트림을 감싸는 작은 유틸의 **자원 수명**을 점검하고 있었다.

  대단한 기능 추가가 아니라, "이 유틸이 다 쓰고 나면 매달아둔 것들을 제대로 떼는가" 를 확인하는 지루한 작업이었다.

- 그러다 한 줄에서 멈췄다. 외부에서 받은 `AbortSignal` 에 리스너를 매다는 흔한 코드였다.

```js
externalSignal.addEventListener("abort", onAbort, { once: true });
```

- `{ once: true }` 가 붙어 있으니 나는 당연히 이렇게 읽었다.

  > "한 번 쓰고 알아서 떨어지겠네."

- 그런데 이게 **정상 종료 경로에서는 영영 떨어지지 않는다**는 걸 뒤늦게 알았다. 이번 글은 이 작은 오독이 만든 리스너 누수와, 그걸 선언적으로 정리하는 법에 대한 기록이다.

---

## 🔗 문제의 구조 — 외부 signal 을 내부로 이어붙이기

### 🧩 흔한 브리지 패턴

- 스트림/리더 같은 유틸은 종종 외부의 취소 신호(`AbortSignal`)를 받아, 내부 취소 컨트롤러로 **이어붙인다**.

  외부가 취소하면 내부도 같이 끊고, 유틸 자체적으로도 `abort()` 로 끊을 수 있게 하기 위해서다.

```js
function createStream(source, { signal } = {}) {
  // 내부 취소는 이 컨트롤러가 소유한다.
  const internal = new AbortController();

  // 외부 signal → 내부 컨트롤러로 브리지
  if (signal) {
    if (signal.aborted) internal.abort();
    else signal.addEventListener("abort", () => internal.abort(), { once: true });
  }

  let settled = false;
  function resolveDone(result) {
    if (settled) return;
    settled = true;
    internal.abort(); // 내부 리더 정리
    // ... queue close, 콜백 호출, done resolve
  }

  // 종료 경로: (1) 정상 terminal 관측  (2) 네트워크 자연 종료  (3) abort()
  // 셋 다 결국 resolveDone 하나로 수렴한다.
  return { done: /* ... */, abort: () => resolveDone({ status: "cancelled" }) };
}
```

- 겉보기엔 멀쩡하다. `{ once: true }` 도 붙어 있으니 리스너 정리도 신경 쓴 것처럼 보인다.

### 🤔 그런데 `{ once: true }` 는 언제 떨어지나?

- MDN 을 다시 읽어보면 정의가 생각보다 좁다.

  > `once` 가 true 이면, 리스너는 **호출된 뒤(after being invoked)** 자동으로 제거된다.

- 핵심은 **"호출된 뒤"** 다. 즉 자동 제거의 트리거는 시간도, GC 도 아니고 **리스너의 발화**다.

  - 외부 signal 이 `abort` 로 **발화하면** → 리스너 실행 → 자동 제거 ✅
  - 외부 signal 이 **끝까지 발화하지 않으면** → 리스너는 그대로 남는다 ❌

- 그런데 스트림이 **정상 종료**되는 경우를 떠올려보자. 사용자가 취소한 게 아니라 서버가 끝까지 응답을 보내고 곱게 끝난 상황이다.

  이때 외부 signal 은 abort 될 일이 없다. `resolveDone` 안에서 우리는 `internal.abort()` 만 부른다.

> 정상 종료에서는 외부 signal 이 발화하지 않으므로, `{ once: true }` 리스너는 **떨어질 트리거가 없다.**

## 🔗 왜 로컬에선 안 보였나 — 누수의 조건

### 🕵️ 짧은 수명이 증상을 가린다

- 이 누수는 아무 상황에서나 터지지 않는다. 두 조건이 겹쳐야 한다.

  1. 외부 signal 이 **오래 산다** (여러 스트림에 걸쳐 재사용되는 공유 signal)
  2. 그 signal 로 유틸을 **반복 생성**한다

- 반대로, 호출마다 새 `AbortController` 를 만들어 넘기는 경우엔 증상이 없다.

  스트림이 끝나 그 컨트롤러를 아무도 참조하지 않으면, 매달린 리스너째로 통째로 GC 되기 때문이다.

- 그래서 단위 테스트나 짧은 로컬 시나리오에선 멀쩡해 보인다. 정작 문제는 이런 코드에서 자란다.

```js
// 세션 하나가 사는 동안 공유되는 long-lived signal
const sessionAbort = new AbortController();

// 같은 세션에서 스트림을 여러 번 여닫는다 (재연결 · 다음 턴 · 재구독 …)
for (const turn of turns) {
  const stream = createStream(await open(turn), { signal: sessionAbort.signal });
  await stream.done; // 정상 종료 → 리스너 1개 잔류
}
// sessionAbort.signal 에는 이제 죽은 리스너가 turns.length 개 쌓여 있다.
```

- 정상 종료가 한 번 일어날 때마다 `sessionAbort.signal` 에 리스너가 **한 개씩 순증**한다. 세션이 길수록 조용히 쌓인다.

### 🔎 확인하는 법

- 크롬 콘솔에서 특정 노드/타깃의 리스너를 직접 셀 수 있다.

```js
getEventListeners(sessionAbort.signal).abort?.length;
// 스트림을 여닫을 때마다 이 숫자가 1씩 커지면 → 누수 확정
```

- "기능은 멀쩡한데 숫자만 커지는" 종류의 버그라, 증상이 눈에 띌 즈음엔 이미 한참 쌓인 뒤다.

## 🔗 고치기 — 종료 경로에서 명시적으로 뗀다

### 1️⃣ 핸들러 참조를 잡고, 종료 퍼널에서 해제

- 첫 번째 수정은 단순하다. 익명 함수 대신 **참조를 잡아두고**, 모든 종료가 수렴하는 `resolveDone` 에서 명시적으로 뗀다.

```js
let detach = () => {};
if (signal) {
  if (signal.aborted) internal.abort();
  else {
    const onAbort = () => internal.abort();
    signal.addEventListener("abort", onAbort);
    detach = () => signal.removeEventListener("abort", onAbort);
  }
}

function resolveDone(result) {
  if (settled) return;
  settled = true;
  internal.abort();
  detach(); // ← 정상 종료든 abort 든, 여기서 반드시 뗀다
  // ...
}
```

- 포인트는 **종료 경로가 하나로 모여 있어야 한다**는 것이다. 정상 terminal · 자연 종료 · `abort()` 가 전부 `resolveDone` 을 통과하므로, 여기 한 줄이면 모든 경로가 커버된다.

- 그리고 `removeEventListener` 는 **멱등**하다. 외부 signal 이 이미 발화해서 리스너가 자동 제거된 뒤에 다시 불러도 조용한 no-op 이라, "발화했을 수도 / 아닐 수도" 를 신경 쓸 필요가 없다.

### 2️⃣ 더 깔끔한 방법 — addEventListener 자신의 `signal` 옵션

- 사실 `addEventListener` 에는 리스너 해제를 **선언적으로** 위임하는 옵션이 있다. 세 번째 인자의 `signal` 이다.

  > 여기 넘긴 `AbortSignal` 이 abort 되면, 이 리스너는 **자동으로 제거된다.**

- 우리는 이미 종료 시 `internal.abort()` 를 부른다. 그러면 외부 리스너 해제를 바로 그 `internal.signal` 에 맡길 수 있다.

```js
if (signal) {
  if (signal.aborted) internal.abort();
  else {
    // internal 이 abort 되면(=우리가 종료할 때) 이 리스너는 알아서 떨어진다.
    signal.addEventListener("abort", () => internal.abort(), {
      signal: internal.signal,
    });
  }
}
```

- 이제 `detach()` 를 손으로 부를 필요도 없다. 두 종료 경로가 하나의 메커니즘으로 정리된다.

  - 외부가 취소 → 리스너 발화 → `internal.abort()` → (internal 이 abort 됐으니) 리스너 자동 제거
  - 정상 종료 → `resolveDone` 이 `internal.abort()` → 리스너 자동 제거

> `{ once: true }` 는 "한 번 발화하면 뗀다" 는 뜻이고,
> `{ signal }` 은 "이 신호가 죽으면 뗀다" 는 뜻이다.
> 우리가 원했던 건 후자였다.

## 🔗 남는 교훈

### 💡 `{ once: true }` 는 정리 전략이 아니다

- `once` 는 **발화 횟수 보장**이지, **수명 관리**가 아니다.

  발화하지 않는 경로가 존재한다면(=정상 종료), `once` 는 그 경로의 리스너를 책임지지 않는다.

- 리스너의 수명은 결국 **누가, 언제 떼는가** 를 명시해야 한다. 방법은 둘 중 하나다.

  - 종료가 수렴하는 지점에서 `removeEventListener` 를 직접 부르거나,
  - `addEventListener(..., { signal })` 로 "이 신호가 죽으면 떼라" 를 선언해두거나.

### 🤔 비슷한 코드를 짜고 있다면

- 외부 `AbortSignal` 을 받아 내부로 브리지하는 유틸을 짜고 있다면, 다음 질문을 던져보면 좋겠다.

  - 이 리스너는 **정상 종료** 경로에서도 떨어지는가?
  - 소비자가 **오래 사는 공유 signal** 을 넘기면 어떻게 되는가?
  - 종료 경로가 여러 개라면, 정리 코드가 그 **전부**를 지나는가?

- 셋 중 하나라도 자신 없다면, `{ once: true }` 대신 `{ signal }` 옵션을 먼저 떠올려보자. 대부분의 브리지 패턴은 이 한 줄로 정리된다.

  😁 공개 API(라이브러리)일수록 이게 중요하다. 소비자가 signal 을 어떻게 넘길지는 내가 정할 수 없으니까 — "오래 사는 signal 로 반복 호출해도 새지 않는다" 까지가 유틸의 계약이라고 생각하게 됐다.
