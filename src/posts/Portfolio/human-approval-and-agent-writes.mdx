## 승인 버튼 하나에도 조건이 꽤 많다

요즘 마케팅 캠페인 도구를 만들고 있다. 에이전트가 후보와 초안을 만들고, 사람이 읽어본 뒤 승인한 내용을 외부로 보내는 도구다. 화면부터 API, 업무 규칙, PostgreSQL 저장 구현까지 맡았다.

이 흐름에서 승인 버튼은 사용자가 읽어본 내용을 보내도 된다는 뜻이다. 그런데 그 버튼을 누르는 사이에 다른 작업이 초안을 고치면 어떻게 될까?

예를 들어 나는 A 버전을 보고 있는데, 서버에는 이미 B 버전이 저장됐다고 해보자. 승인 요청에 초안 ID만 보내면 서버는 지금 저장된 B 버전을 승인할 수 있다. 내가 읽어본 문장이 아닌 것이다.

이 문제에 재시도로 생기는 중복 기록과 에이전트의 수정 권한까지 더해졌다. 화면에서 버튼만 비활성화해서는 다른 탭이나 에이전트의 요청을 막을 수 없으니, 서버 쪽에서도 기준이 필요했다.

## 내가 본 버전도 같이 보내면 된다

초안의 버전을 승인 요청에 넣고, 서버가 가진 버전과 비교하도록 했다. 다르면 승인하지 않고 최신 내용을 다시 보여준다. 같으면 비교와 승인 처리를 같은 트랜잭션 안에서 진행한다.

판단 순서만 줄여보면 아래와 같다. 저장소 함수나 오류 처리는 생략했다.

```ts
await transaction(async (tx) => {
  const current = await lockDraft(tx, request.id);

  if (current.version !== request.version) {
    throw new Error("승인하기 전에 초안이 변경됐다.");
  }

  await markApproved(tx, current.id, current.version);
});
```

버전 필드를 하나 붙였다고 끝나는 일은 아니다. 비교 직후 다른 요청이 내용을 바꿀 수 없도록 저장 과정도 맞춰야 한다. 승인 뒤에 수정하는 경우나 실제 발송 직전에도 같은 기준을 확인해야 한다.

### 여러 개를 한꺼번에 승인한다면?

초안을 여러 개 골라 승인할 때 하나만 충돌하면 어떻게 처리할지도 정해야 했다. 되는 것만 승인할지, 전부 거부하고 다시 검토하게 할지의 문제다.

제품 소유자와 이야기해서 후자로 정했다. 일부만 성공하면 사용자가 승인된 목록과 실패한 목록을 다시 맞춰봐야 한다. 전부 거부하면 재검토하는 수고는 생기지만, 이번 요청이 적용됐는지는 분명해진다.

두 사람이 겹치는 묶음을 동시에 승인하는 경우도 검사했다. 같은 순서로 기록을 잠가 교착 가능성을 줄이고, 하나라도 충돌하면 전체가 되돌려지는지 실제 DB에서 확인했다.

## 같은 요청을 두 번 보냈다고 두 개가 생기면 곤란하다

생성 요청을 보냈는데 응답이 안 왔다고 해보자. 서버가 만들기 전에 실패했을 수도 있고, 만들기는 했는데 응답만 못 받았을 수도 있다. 이 상태에서 다시 생성하면 같은 후보나 초안이 두 개 생길 수 있다.

그래서 생성 요청에 `Idempotency-Key`를 사용할 수 있게 했다. 같은 작업에서 같은 키와 같은 내용을 다시 보내면 처음 만든 기록을 돌려준다. 같은 키에 다른 내용을 넣으면 충돌로 처리한다.

여기서 단순히 기존 키를 조회한 뒤 없으면 생성하는 것만으로는 부족하다. 두 요청이 동시에 조회하면 둘 다 없다고 볼 수 있기 때문이다. 실제로는 작업 범위를 잠근 같은 트랜잭션 안에서 조회하고 기록한다.

```text
트랜잭션 시작
  → 작업 범위를 잠그고 현재 시도와 권한을 확인
  → 같은 키가 있으면 요청 내용도 같은지 확인
      · 같으면 기존 결과 반환
      · 다르면 충돌로 거부
  → 키가 없으면 기록 생성과 키 저장
트랜잭션 완료
```

멱등 키와 버전 검사는 둘 다 중복 문제처럼 보일 수 있지만 용도가 다르다. 멱등 키는 같은 요청을 다시 보낸 것인지 확인하고, 버전 검사는 내가 봤던 내용과 지금 내용이 같은지 확인한다.

외부 발송은 여기서 한 번 더 조심해야 했다. 서버 안의 생성 요청을 멱등하게 처리했다고 외부 서비스로 나간 메일까지 무조건 다시 보낼 수 있는 건 아니다. 응답을 받지 못한 발송은 결과를 확인할 수 없는 상태로 두고, 외부 기록을 대조한 뒤 사람이 확정하게 했다.

## 에이전트는 자기가 맡은 작업 안에서만 쓴다

에이전트 역할이라고 해서 아무 캠페인의 기록이나 고칠 수 있게 둘 수는 없었다. 요청에서 실행 중인 작업 시도의 ID를 확인하고, 그 작업에 속한 캠페인과 기록만 다루도록 범위를 좁혔다.

작업 시도에는 유효 시간도 뒀다. 진행 보고가 끊겨 만료됐거나, 작업이 취소·완료됐다면 이전 시도의 쓰기는 거부한다. 뒤늦게 도착한 요청이 새 작업의 결과를 건드리지 않도록 한 것이다.

에이전트는 자신이 만든 승인 전 기록만 수정하거나 삭제할 수 있다. 승인·발송·게시는 사람이 실행한다.

| 확인할 대상 | 적용한 기준                            |
| ----------- | -------------------------------------- |
| 작업 시도   | 현재 실행 중이며 기한이 남아 있는가    |
| 캠페인      | 맡은 작업의 캠페인과 일치하는가        |
| 기록        | 해당 작업이 만든 승인 전 기록인가      |
| 행위        | 에이전트에게 허용된 생성·수정·삭제인가 |

## 이 규칙들은 어디에 둘까?

버전 충돌이나 일괄 승인 거부 같은 판단은 프레임워크에 의존하지 않는 업무 규칙으로 분리했다. 인증과 헤더를 읽는 일은 서버에서, 잠금과 트랜잭션은 저장 계층과 서버 서비스에서 맡는다.

```text
화면                   검토 내용 표시 · 충돌 안내 · 재조회
  ↓
API·서버 서비스        인증 · 입력 검사 · 작업 범위 확인 · 처리 조립
  ↓
업무 규칙              승인 조건 · 수정 권한 · 상태 전이 판단
  ↓
PostgreSQL             잠금 · 트랜잭션 · 기록과 멱등 키 저장
```

화면에서는 무엇을 다시 검토해야 하는지 안내한다. 요청·응답 스키마와 에이전트용 OpenAPI도 함께 관리해서 화면과 에이전트가 같은 계약을 보도록 했다.

승인한 게시 계획의 예약 기록은 승인과 같은 트랜잭션에서 만들었다. 승인만 되고 예약이 빠지는 상태를 피하기 위해서다. 여기서 묶은 범위는 이 처리 경로이고, 모든 편집이나 외부 호출까지 하나의 트랜잭션에 넣은 것은 아니다.

## 실제로 확인한 범위

버전 충돌과 중복 요청은 실제 PostgreSQL을 사용하는 테스트로 확인했다. 브라우저에서는 충돌 안내나 다시 불러온 내용, 여러 탭에서 선택한 캠페인처럼 사용자가 보는 흐름을 검사했다. 재현할 수 있는 결함은 고치기 전 실패하고 고친 뒤 통과하는 테스트로 남겼다.

처음 글을 정리한 2026년 10월 19일에는 실계정 검증과 첫 운영 배포가 남아 있었다. 이후 진행 상황도 10월 29일 기준으로 덧붙인다.

- 10월 20일 로컬에서 실제 Gmail 연결, 시험 메일 발송, 답장 확인을 진행했다. 이때 인증 오류 안내와 승인 화면의 문제를 수정했다.
- 후속 작업에서 첫 운영 배포를 마쳤다. 실제 계정 연결과 보안 검토에서 나온 문제는 회귀 테스트와 함께 확인했다.
- 지금은 첫 배포와 일부 계정의 검증을 마친 상태다. 나머지 외부 서비스의 실계정 검증, 실제 에이전트 실행 연동, 회사 공통 연동 구조의 적용은 별도로 확인해야 한다.

승인 버튼을 만드는 일이 서버에서 승인 여부 하나만 바꾸는 것으로 끝나지는 않았다. 어떤 내용을 보고 승인했는지, 같은 요청이 다시 온 건지, 누가 어느 작업에서 고치는 건지까지 이어져 있었다.

버전이 바뀌면 다시 읽어봐야 하고 발송 결과를 모르면 사람이 확인해야 한다. 이 과정이 사용자에게는 번거로울 수 있다. 그래서 거부하는 규칙을 넣는 것과 함께, 왜 다시 확인해야 하는지도 화면에서 설명하려고 했다.
