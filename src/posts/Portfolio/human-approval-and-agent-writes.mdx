# 🗂️ 사람이 승인한 것만, 에이전트는 맡은 범위만

---

## 🔗 맥락

- Smoody Scouter는 마케팅 캠페인에서 후보·초안·답장·게시 계획을 관리하는 Next.js 16 · PostgreSQL 제품이다. 에이전트는 탐색·초안·답장 초안 작업을 맡고, 사람이 검토·승인한 것만 연결한 계정으로 발송·게시한다.
- 하나의 팀이 쓰는 서비스이며, 화면 · Route Handler · 도메인 규칙 · PostgreSQL 저장 구현을 모두 제가 담당했다. 프론트엔드에서 출발해 제품의 서버 경계까지 다룬 경험이다.
- 이 글을 쓰는 시점에 운영 첫 릴리스와 외부 공급자 실계정 검증은 진행 중이다. 아래는 구현과 검사가 끝난 범위만 다룬다.

## 🔗 문제 — 사람과 에이전트가 같은 기록을 건드린다

- 사람이 초안을 승인한 뒤 에이전트가 같은 초안을 고치면, 승인자는 자기가 본 적 없는 내용을 발송하게 된다.
- 에이전트가 요청을 재전송하면 같은 후보·초안이 두 번 만들어진다. 에이전트는 네트워크 오류 뒤에 재시도하는 것이 정상 동작이라 막을 수 없다.
- 에이전트가 맡은 작업과 무관한 캠페인의 기록을 만들거나 고칠 수 있었다. 작업 범위를 제한하는 장치가 없었다.
- "관리자 화면 CRUD"로 보면 간단하지만, 실제 사용자 문제는 **잘못된 대상을 승인하거나 오래된 내용을 발송하는 것**이었다.

## 🔗 제약

- 승인·발송·게시는 사람만 할 수 있어야 한다. 에이전트 키로는 승인·팀 관리·사용자 작업 요청을 수행할 수 없다.
- 우리 서버가 에이전트를 직접 부르는 연결부는 아직 없다. 에이전트는 대기 요청 목록을 가져가 시작·진행·완료를 보고하는 구조라, 서버는 "지금 이 쓰기가 어떤 작업의 몇 번째 시도인가"를 요청 자체에서 알아내야 한다.
- 발송·게시는 외부 효과다. 결과 불명이면 자동 재시도하지 않고 한 번만 실행해야 한다.

## 🔗 선택지

| ---------------------- | ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |

## 🔗 결정 — 규칙을 도메인 한 곳에 두고 화면·API·DB가 같은 규칙을 쓴다

### 승인 버전 검사와 일괄 승인

- 승인은 게시 계획(또는 초안)을 잠근 트랜잭션 안에서 버전을 비교한다. 충돌 코드는 버전 충돌·대상 없음·닫힌 캠페인 세 가지다.
- 일괄 승인은 항목을 ID 순으로 정렬해 잠근다(교착 방지). 하나라도 충돌 코드가 나오면 전체를 거부하고 어떤 항목이 왜 실패했는지 돌려준다. 화면은 확인 창과 함께 그 목록을 보여 준다.
- 승인과 예약 게시 등록은 **한 트랜잭션**이다. 승인은 됐는데 예약이 안 들어가는 상태를 만들지 않는다. 예약 실행 기록은 게시 계획 ID와 버전으로 만든 멱등 키로 한 번만 만들고, 실행기는 커밋된 `queued` 기록만 가져간다.

### 에이전트 쓰기 범위

- 에이전트 키로 기록을 쓰려면 `start`로 받은 attempt ID를 헤더에 넣어야 한다. 서버는 그 시도를 잠그고 다음을 확인한다.
  - 시도가 살아 있는가: 시작·진행 보고 뒤 **수 분 단위의 lease**. 지났으면 만료로 거부하고 "다른 시도가 시작했을 수 있으니 멈춰 달라"고 안내한다.
  - 취소·종료되지 않았는가. 시도 횟수에는 상한이 있다.
  - 그 작업의 **캠페인**과 같은가. 다르면 거부한다.
  - 만든 기록은 작업 요청에 연결한다. 결과 검토 화면이 "이 요청이 만든 것"을 필터할 수 있다.
- 멱등 키는 길이와 문자 집합을 제한한다. 후보·초안·게시글만 멱등 키를 보존한다.
- 에이전트는 자기가 만든 승인 전 후보·초안·게시글만 고치거나 지운다. 캠페인은 읽기만 한다. 후보 선택은 사람이 한다.

### 경계

- 도메인 규칙은 프레임워크를 모른다. Route Handler는 인증 뒤 도메인 진입 함수를 부르고 결과를 HTTP로 옮기는 일만 한다.
- 요청·응답 스키마는 Zod 하나로 정의하고, 여기서 에이전트용 OpenAPI를 만든다. 사람용 API와 에이전트용 API가 같은 계약을 공유한다.
- 역할은 뷰어·에디터·관리자·소유자다. 프런트의 비활성 표시와 별개로 서버가 매 요청 검사한다. 팀 설정 저장은 현재 revision을 요구하고 충돌 시 409다.

## 🔗 확인 결과

- `npm run check`는 정적 검사 · 단위/DB · 빌드 · 재시작 보존 · HTTP · 흐름 · 디자인 · 설정/기능 검사를 한 번에 돌린다. 단위·DB 검사 수백 개와 HTTP·브라우저 흐름·디자인·설정 검사 수백 개가 돌아간다. 검사 수는 그 시점의 검증 범위이지 품질 자체의 증명은 아니다.
- 각 결함 수정은 **수정 전 실패 · 수정 후 통과** 를 확인하는 검사를 함께 넣었다. 다중 탭에서 열린 게시 창의 캠페인 고정, 같은 분 안의 답장 시각 보존, 무효 요청 뒤 정상 대기열 처리가 그 예다.
- 운영 역할의 CRUD 허용과 DDL·이력 변경 거부는 실제 격리된 PostgreSQL 역할로 확인했다. 로컬과 CI 모두 실제 PostgreSQL을 쓴다.
- 앱 안 예약 실행에는 중복 실행을 피하는 DB 잠금과 실패 시 대기 간격 조정이 있다.

## 🔗 남은 제약과 현재 상태

- 편집 경로의 예약 동기화는 아직 트랜잭션 밖에서 맞춘다. 승인 경로만 한 트랜잭션이다.
- 우리 서버가 에이전트를 호출하는 연결부는 없다. 에이전트는 대기 요청을 가져가는 쪽이다.
- 외부 공급자 연동 코드는 있으나 실계정 검증이 남아 있다. 공급자 키가 없으면 화면은 "연결 준비 안 됨"으로 표시한다.
- 클라우드 배포 구성은 준비 단계이고, 운영 첫 릴리스는 아직이다.

## 🔗 면접에서 받을 질문에 대한 답

- **멱등성과 버전 충돌은 각각 어떤 문제를 막는가?** 멱등 키는 "같은 요청이 두 번 와도 한 번만 만든다"로 중복 생성을 막는다. 버전 검사는 "내가 본 것과 지금 것이 같은가"로 오래된 내용의 승인·발송을 막는다. 둘은 다른 실패를 다루므로 하나로 대체되지 않는다.
- **왜 부분 승인을 허용하지 않았나?** 승인은 사람이 책임지는 행위다. 일부만 승인되면 승인자는 결과 목록을 다시 대조해야 하고, 그 사이 또 바뀔 수 있다. 전체 거부 뒤 재요청이 더 단순하다.
