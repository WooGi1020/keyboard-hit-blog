# 승인한 초안과 발송된 초안은 같은 것일까?

> 작업 시기: 2026.10 · 정리: 2026.10

---

## 🔗 들어가며

### 승인 뒤에 초안이 바뀌어 있었다

- 마케팅 캠페인 도구를 만들고 있다. 에이전트가 후보를 찾고 초안을 쓰면, 사람이 검토해서 승인한 것만 연결된 계정으로 나가는 구조다.

- 개발 중에 이런 장면을 봤다. 내가 초안 하나를 승인했다. 그 사이 에이전트가 같은 초안을 "더 낫게" 고쳤다. 발송 큐에는 **내가 본 적 없는 문장**이 들어가 있었다.

> 승인은 "이 내용을 보내도 된다" 는 뜻인데, 그 "이 내용" 이 승인 뒤에 바뀔 수 있다면 승인은 아무 의미가 없다.

- 비슷한 문제가 두 개 더 보였다. 에이전트가 네트워크 오류 뒤에 재시도하면 같은 후보가 **두 번** 생겼고, 에이전트 키 하나로 **아무 캠페인**의 기록이나 만들 수 있었다.

- 이번 글은 이 세 문제를 "관리자 화면 CRUD" 가 아니라 **사용자가 잘못된 것을 승인하거나 보내지 않게 하는 규칙**으로 보고 풀어 본 기록이다. 프론트엔드에서 출발했지만 Route Handler 와 PostgreSQL 저장 구현까지 내가 맡은 프로젝트라, 규칙을 어디에 둘지부터 정해야 했다.

---

## 🔗 문제 하나 — "내가 본 것" 과 "지금 것" 이 같은가

### 승인 요청에 ID 만 보내고 있었다

- 처음 승인 API 는 이랬다.

```ts
// POST /api/v1/drafts/:id/approve
await approveDraft(params.id);
```

- ID 만 보내니 서버는 "지금 저장된 내용" 을 승인한다. 사용자가 **화면에서 본 내용**이 뭔지는 아무도 모른다.

### 버전을 같이 보낸다

- 고치는 방법은 단순했다. 초안마다 `version` 을 두고, 승인 요청이 **자기가 본 버전**을 함께 보낸다. 서버는 잠근 상태에서 비교한다.

```ts
// 클라이언트 — 화면이 렌더한 그 버전을 그대로 보낸다
await approveDraft({ id: draft.id, version: draft.version });

// 서버 — 트랜잭션 안에서 잠그고 비교한다
await db.transaction(async (tx) => {
  const current = await tx.lockDraft(id); // SELECT ... FOR UPDATE
  if (current.version !== version) throw new DomainError("VERSION_CONFLICT");
  if (current.campaignClosed) throw new DomainError("CAMPAIGN_CLOSED");
  await tx.markApproved(id, approver);
});
```

- 충돌이 나면 화면은 "내용이 바뀌었으니 다시 확인하라" 고 보여 주고, 사용자는 새 버전을 보고 다시 결정한다. 승인이 다시 "내가 본 것" 에 대한 행위가 됐다.

### 일괄 승인에서 하나만 충돌하면?

- 초안 수십 개를 한 번에 승인하는 화면이 있다. 그중 하나가 충돌하면 어떻게 할까. 두 가지 길이 있었다.

  - 되는 것만 승인하고 실패 목록을 보여 준다
  - 하나라도 충돌하면 **전부 거부**한다

- 제품 소유자와 이야기해 후자로 정했다. 부분 성공은 승인자가 "그래서 뭐가 승인된 거지" 를 결과 목록과 다시 대조하게 만들고, 그 사이에 또 바뀔 수 있다. 전부 거부하고 다시 요청하는 쪽이 사람에게 단순했다.

```ts
export function batchRejection(failures: BatchFailure[]): DomainError | null {
  if (failures.length === 0) return null;
  // 하나라도 충돌(버전·대상 없음·닫힌 캠페인)이면 전체를 거부하고 목록을 돌려준다
  return new DomainError("BATCH_REJECTED", { failures });
}

// 잠금은 항상 ID 순서로 — 두 사람이 겹치는 묶음을 동시에 승인해도 교착이 안 난다
const inLockOrder = (items: Item[]) => [...items].sort((a, b) => a.id.localeCompare(b.id));
```

## 🔗 문제 둘 — 같은 요청이 두 번 오면

### 재시도는 에이전트의 정상 동작이다

- 에이전트는 네트워크가 흔들리면 재시도한다. 막을 수도 없고 막아서도 안 된다. 그런데 `POST /candidates` 를 두 번 받으면 후보가 둘 생긴다.

### 멱등 키 — "이 요청은 아까 그 요청이다"

- 쓰기 요청에 `Idempotency-Key` 헤더를 받는다. 같은 키가 다시 오면 새로 만들지 않고 **아까 만든 기록**을 돌려준다.

```ts
const key = request.headers.get("Idempotency-Key"); // 길이와 문자 집합을 제한한다

const existing = key ? await repo.findByIdempotencyKey(key) : null;
if (existing) return json(existing, { headers: { "Idempotent-Replay": "true" } });

const created = await repo.createCandidate({ ...input, idempotencyKey: key });
return json(created, { status: 201 });
```

- 여기서 한 가지를 분명히 해 두고 싶다. 멱등 키와 버전 검사는 **다른 실패**를 막는다.

> 멱등 키는 "같은 요청이 두 번 와도 한 번만 만든다" — 중복 생성을 막는다.
> 버전 검사는 "내가 본 것과 지금 것이 같은가" — 오래된 내용의 승인을 막는다.
> 하나로 다른 하나를 대신할 수 없다.

## 🔗 문제 셋 — 에이전트는 어디까지 써도 되나

### 키 하나로 모든 캠페인에

- 에이전트용 API 키는 역할만 검사했다. "에이전트 역할이면 후보를 만들 수 있다." 그러면 어느 캠페인에든 만들 수 있다는 뜻이 된다.

### 쓰기를 "맡은 작업 시도" 하나에 묶는다

- 우리 서버가 에이전트를 부르는 게 아니라, 에이전트가 대기 요청을 가져가 `start → progress → complete` 를 보고하는 구조다. 그래서 `start` 가 돌려준 **시도 ID** 를 쓰기 요청마다 헤더로 받고, 서버가 그 시도를 잠근 뒤 확인한다.

```ts
export async function agentWriteOf(request: Request, resource: Resource) {
  const attemptId = request.headers.get("X-Agent-Attempt");
  if (!attemptId) throw attemptRequired();

  const attempt = await repo.lockAttempt(attemptId);
  if (!attempt || attempt.canceled) throw rejectAgentWork("ATTEMPT_STALE");
  if (isLeaseExpired(attempt)) throw rejectAgentWork("ATTEMPT_STALE", leaseExpiredMessage);

  return {
    // 맡은 작업의 캠페인에만 쓴다
    assertCampaign(campaignId: string) {
      if (attempt.campaignId !== campaignId) throw outOfScope();
    },
    // 만든 기록은 작업 요청에 연결한다 — 결과 검토 화면이 "이 요청이 만든 것" 을 필터한다
    link: { workRequestId: attempt.workRequestId, attemptId },
  };
}
```

- 시도에는 **짧은 lease** 가 있다. 진행 보고가 끊긴 채 시간이 지나면 만료로 거부하고, "다른 시도가 시작했을 수 있으니 멈춰 달라" 는 메시지를 돌려준다. 시도 횟수에도 상한이 있다.

- 그리고 에이전트는 **자기가 만든 승인 전 기록**만 고치거나 지운다. 캠페인은 읽기만 하고, 후보 선택은 사람이 한다. 승인 · 발송 · 게시 API 는 에이전트 키로 아예 열리지 않는다.

## 🔗 규칙을 어디에 둘 것인가

### ⬇️ 도메인 → Route Handler → 화면

- 세 규칙 모두 **도메인 함수**에 있다. Route Handler 는 인증을 확인하고 도메인 함수를 부른 뒤 결과를 HTTP 로 옮기는 일만 한다.

```text
화면 (Next.js)        버튼 비활성 · 충돌 안내 · 확인 창        ← 안내일 뿐, 검사가 아니다
      │
Route Handler         인증 → 도메인 함수 호출 → HTTP 상태 코드   ← 얇다
      │
도메인 규칙           버전 비교 · 전체 거부 · 멱등 키 · 작업 범위  ← 프레임워크를 모른다
      │
PostgreSQL            FOR UPDATE 잠금 · 트랜잭션 · 멱등 키 유니크
```

- 요청 · 응답 스키마는 Zod 하나로 정의하고 거기서 에이전트용 OpenAPI 를 뽑는다. 사람용 API 와 에이전트용 API 가 **같은 계약**을 본다.

### 승인과 예약을 한 트랜잭션에

- 승인된 게시 계획은 예약 실행 큐에 들어간다. 이 둘을 따로 하면 "승인은 됐는데 예약이 없는" 상태가 생길 수 있어서, 승인 트랜잭션 안에서 예약 기록까지 만든다. 실행 기록은 게시 계획 ID 와 버전으로 만든 멱등 키로 **한 번만** 생기고, 실행기는 커밋된 `queued` 만 가져간다.

  다만 편집 경로의 예약 동기화는 아직 트랜잭션 밖이다. 승인 경로만 먼저 묶었다.

## 🔗 지금 어디까지 왔나

### 검사

- `npm run check` 하나로 정적 검사 · 단위/DB · 빌드 · HTTP · 브라우저 흐름 · 디자인 회귀가 다 돈다. 로컬도 CI 도 실제 PostgreSQL 을 쓴다.

- 결함을 고칠 때는 **고치기 전 실패 → 고친 뒤 통과** 를 보여 주는 검사를 같이 넣었다. 다중 탭에서 열린 게시 창의 캠페인 고정, 같은 분 안의 답장 시각 보존 같은 것들이다.

### 아직 아닌 것

- 외부 공급자 연동 코드는 있지만 실계정 검증이 남았다. 공급자 키가 없으면 화면은 "연결 준비 안 됨" 으로 표시한다.
- 우리 서버가 에이전트를 직접 호출하는 연결부는 없다. 에이전트는 대기 요청을 **가져가는** 쪽이다.
- 클라우드 배포 구성은 준비 단계이고, 운영 첫 릴리스는 아직이다.

  이 글을 쓰는 시점의 상태를 그대로 적어 둔다. "다 됐다" 고 쓰고 싶은 마음은 있지만, 그러면 이 글이 승인 뒤에 바뀐 초안이 된다.

## 🔗 남는 교훈

### 사람의 결정은 "그때 본 것" 에 대한 결정이다

- 승인 · 발송 · 게시처럼 사람이 책임지는 행위는, 그 사람이 **무엇을 보고** 결정했는지가 데이터에 남아야 한다. 버전이 그 역할을 한다.

- 에이전트의 쓰기는 **어떤 작업의 몇 번째 시도**인지가 요청 자체에 남아야 한다. 역할만으로는 부족하다.

> 화면의 비활성 버튼은 안내다. 검사는 서버가, 규칙은 도메인이, 잠금은 DB 가 한다.

### 사람과 에이전트가 같은 데이터를 건드리는 제품이라면

- 다음 질문을 던져보면 좋겠다.

  - 승인 요청에 **버전**이 실려 가는가, ID 만 가는가?
  - 에이전트가 같은 요청을 두 번 보내면 기록이 **몇 개** 생기는가?
  - 에이전트 키 하나로 **어디까지** 쓸 수 있는가?

- 셋 다 자신 있게 답할 수 없다면, 승인 API 에 `version` 한 필드를 추가하는 것부터 시작해 보자. 가장 싸고 가장 많은 사고를 막는다.

  이 작업 뒤로는 "승인" 이라는 버튼을 볼 때마다 "그래서 뭘 승인하는 건데" 를 속으로 묻게 됐다. 내가 만든 화면에서도.
