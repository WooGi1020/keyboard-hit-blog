## 완료라고 뜨는데 서버는 아직 실행 중이었다

에이전트 채팅 화면을 만들면서 연결이 끊겼는데 화면에는 완료로 표시되는 문제를 만났다.

화면만 보면 답변이 다 끝난 것 같다. 그런데 서버에서는 아직 실행 중이고, 그 사이 다음 메시지를 보내면 이전 실행에 새 실행이 겹칠 수 있었다. 취소도 비슷했다. 취소 API의 응답을 받고 바로 다음 메시지를 보내면, 서버가 이전 실행을 멈추기 전에 새 실행이 시작될 수 있었다.

연결이 끝난 것과 작업이 끝난 것을 같은 상태로 다루고 있었던 것이다. 이번 글에서는 이 둘을 나누면서 손본 부분을 정리해보려고 한다.

실행 한 건은 `run`이라고 부르겠다. 아래 코드는 동작을 설명하기 위해 줄인 예시이고, 실제 SDK의 내부 API와는 다르다. 이벤트 처리 코드를 나눈 앞선 작업은 [Translator + Dispatcher 패턴](/posts/React/event-translator-dispatcher-pattern) 글에 정리해뒀다.

## 스트림을 다 읽었으니 실행도 끝났다?

처음의 판단을 코드로 줄여보면 이런 모양이다.

```ts
// 문제가 있던 판단을 단순화한 예시
for await (const event of streamSseEvents(response)) {
  dispatch(event);
}

// 반복문 종료만으로 실행 완료를 판단하고 있었다.
finishRun("completed");
```

반복문이 끝났으니 실행도 마감한다. 서버가 종결 이벤트를 보내고 연결을 닫았다면 문제없다. 그런데 네트워크 때문에 중간에 끊긴 경우라면?

클라이언트가 더 이상 읽을 수 없게 됐을 뿐, 서버의 작업이 끝났는지는 아직 모른다. 이때도 완료로 옮겨버리니 화면과 서버의 상태가 달라졌다.

여기에 이벤트가 오지 않는 상황까지 섞이면 더 헷갈린다. 사용자 입력을 기다리는 실행은 스트림이 열려 있어도 한동안 조용할 수 있다. 조용한 것과 연결이 닫힌 것도 따로 봐야 한다.

### 연결과 실행을 따로 보자

상태를 확인할 때 묻는 질문부터 나눴다.

- **연결 상태:** 지금 서버의 이벤트를 받을 수 있는가?
- **실행 상태:** 서버에서 작업이 진행 중인가, 입력을 기다리는가, 끝났는가?

연결이 끊기면 연결 상태를 바꾸고 다시 붙는다. 이 일만으로 실행까지 완료로 바꾸지는 않는다. 실행 결과는 서버의 종결 이벤트나 재조회한 서버 상태로 확인한다.

### 취소 요청도 접수와 완료가 다르다

취소 API가 돌려주는 `202 Accepted`도 같은 관점에서 봤다. 요청을 받았다는 응답이지, 실행을 멈췄다는 응답은 아니다.

그래서 이 응답만 받고 진행 중인 실행을 지우거나 다음 메시지를 보내지 않도록 했다. 종료가 확인된 뒤에는 완료·오류·취소를 구분한다. 취소를 요청하는 사이에 실행이 먼저 완료될 수도 있으니, `run.cancelled` 하나만 기다리는 것도 맞지 않는다.

```ts
// 종결 이벤트의 의미를 구분하는 설명용 예시
function outcomeOf(type: "run.completed" | "run.error" | "run.cancelled") {
  switch (type) {
    case "run.completed":
      return "completed";
    case "run.error":
      return "failed";
    case "run.cancelled":
      return "cancelled";
  }
}
```

사용자 입력 대기도 종료가 아니다. 입력을 받기 전까지 실행의 맥락을 유지하고, 응답 제출이 접수되면 후속 이벤트를 이어서 받는다.

## 연결이 끊긴 사이에 끝났으면 어떻게 알까?

여기서 한 가지가 더 남는다. 연결이 끊긴 동안 서버의 실행이 끝나버리면 클라이언트는 종결 이벤트를 못 받을 수도 있다. 이벤트를 직접 봐야만 끝낼 수 있게 만들면 이번에는 화면이 계속 진행 중으로 남는다.

복구할 때 서버의 현재 상태를 다시 읽는 이유다. 진행 중인 실행이 있으면 그 스트림에 다시 붙고, 없으면 입력 잠금을 풀고 저장된 대화를 다시 가져온다. 끊긴 사이에 놓친 답변도 이때 채운다.

다만 진행 중인 실행이 없다고 해서 성공했다는 뜻은 아니다. 입력할 수 있는 상태로 돌아오는 것과 완료 알림을 띄우는 것은 별개로 처리했다.

답변 저장 시점도 신경 써야 했다. 종결 이벤트는 왔는데 서버에 저장된 메시지는 아직 덜 채워져 있는 경우가 있었다. 이걸 그대로 화면에 덮으면 방금 보던 답변이 오히려 짧아진다. 로컬 본문과 서버의 확정 메시지를 구분하고, 재조회한 내용이 더 불완전할 때는 덮어쓰지 않도록 했다.

테스트에는 이런 경우들을 넣었다.

- 실행은 수락됐는데 첫 스트림 연결이 실패한 경우
- 연결이 끊긴 사이 실행이 끝나고 답변이 저장된 경우
- 종결 이벤트와 확정 메시지의 도착 시점이 다른 경우
- 취소를 요청했지만 종료 여부는 아직 확인하지 못한 경우

## 본문이 바뀔 때 다른 화면까지 다시 그려야 할까?

SDK를 정리하면서 통신, 대화 상태 관리, React 연동의 책임도 나눴다. 통신 쪽에서는 HTTP·인증·SSE 프레임을 다루고, 대화 런타임에서 실행과 복구를 판단한다. React에서는 화면에 필요한 상태를 구독한다.

```text
통신 처리        HTTP · 인증 · SSE 프레임
     ↓
대화 런타임      실행 · 입력 대기 · 취소 · 기록 재조회
     ↓
React 연동       화면에서 필요한 상태만 구독
```

여기서 실시간 본문과 저장된 메시지 목록은 바뀌는 빈도가 다르다. 본문은 초당 수십 번 바뀌는데, 메시지 목록은 그렇게 자주 바뀌지 않는다. 둘을 같이 구독하면 본문에 글자가 붙을 때마다 관계없는 화면까지 다시 그려진다.

그래서 본문을 그리는 컴포넌트에서 그 상태만 따로 구독하게 했다.

```tsx
// 메시지 목록을 표시하는 컴포넌트
const messages = useChatSessionSelector(controller, (state) => state.messages);

// 실시간 본문을 표시하는 컴포넌트
const streamingText = useChatSessionSelector(controller, (state) => state.streamingText);
```

패키지 출력도 모듈 단위로 바꿨다. 작은 상태 판별 함수 하나를 가져오는데 제품 스키마까지 따라오던 비용을 줄이기 위해서다. 여기서 줄어든 것은 해당 기능만 가져오는 소비 경로의 크기이고, 제품 앱 전체 번들이 같은 비율로 줄어든 것은 아니다.

## 정리하면서 남은 것

상태를 나눴으니 확인해야 할 경우의 수도 늘었다. 대신 연결 실패인지, 입력 대기인지, 취소가 접수된 것인지 따로 재현해서 볼 수 있게 됐다. 완료로 보낼 근거가 없는 상태를 억지로 완료에 넣지 않아도 된다.

장시간 연결이나 강제 연결 절단을 포함한 시나리오, 브라우저 CPU·메모리 사용량은 아직 별도로 검증해야 한다. 상태 전이 테스트가 통과했다고 장시간 사용까지 확인한 셈으로 적어두지는 않으려고 한다.
