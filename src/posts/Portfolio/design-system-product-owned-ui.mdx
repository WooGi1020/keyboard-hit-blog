# 🎨 공통화는 늘리는 것만큼 줄이는 때를 아는 것이다

---

## 🔗 맥락

- Smoody Design System은 브랜드 팔레트와 디자인 토큰을 CSS · Tailwind · JavaScript · 타입 선언으로 생성하고, Base UI 기반 UI 패키지, 생성형 응답 블록(genui), CLI와 MCP 문서 조회를 제공하는 모노레포다. 패키지는 `tokens · ui · genui · cli` 네 개다.
- 몇 달에 걸쳐 여러 버전을 사내 비공개 패키지 저장소에 발행했다. 토큰 수백 개, UI 공개 API 수십 개, 생성형 응답 블록 열 개 안팎이 저장소의 구성 규모다.
- 이 사례는 첫 소비 제품을 붙인 뒤 내린 결정에 관한 것이다. **공통 UI의 범위를 실제 제품에 맞춰 줄였다.**

## 🔗 먼저 만든 것 — 정본·생성물·소비 제품 사이의 계약

- **토큰 생성 파이프라인**: 토큰 JSON을 정본으로 두고 CSS 변수 · Tailwind 프리셋 · JS 상수 · 타입 선언을 생성한다. 토큰마다 출처를 보존한다.
- **차이 검사(drift gate)**: 빌드 전 생성물을 스냅샷하고 다시 생성한 뒤 비교한다. 손으로 고친 생성물이나 오래된 생성물은 게이트에서 실패한다. 정본과 생성물이 갈라지는 것을 CI가 막는다.
- **라이브러리 PoC**: Base UI · React Aria Components · Ark UI를 같은 토큰 위에서 Dialog · Select · Combobox · Menu × 2 surface로 똑같이 구현해 비교했다. 평가 축은 포털 × surface 주입, 상태 data 속성 커버리지, 래퍼 두께, Combobox 필터링 배선, axe 감사, 구현 중 실제로 겪은 DX 사고, 번들이다. "Base UI 채택 결정에 대한 반증 시도"로 프레이밍했고 반증에 실패해 Base UI를 확정했다.
- **SurfaceRoot**: React Context와 `data-surface` DOM 스코프를 하나의 API로 묶는다. UI 패키지의 모든 Popup · Backdrop 래퍼는 이 값을 자기 `data-surface`로 다시 찍는다. 포털로 `document.body`에 나가도 표면 토큰을 잃지 않기 위한 규약이고, PoC에서 세 라이브러리 모두에서 성립함을 확인했다.
- **검증**: 독립 설치 fixture로 실제 tarball을 소비해 CSS · Tailwind · ESM · 타입이 설치되는지 확인한다. 세 브라우저 계약 검사, 시각 회귀, axe 자동 접근성·대비 검사를 발행 게이트에 두었다. 자동 검사는 전체 접근성 인증을 뜻하지 않는다.
- **CLI와 MCP**: 같은 manifest와 조회 함수를 공유한다. 개발자는 CLI로, 에이전트는 stdio MCP로 설치한 버전의 문서를 조회한다. 서비스 브랜드색 하나에서 대비를 검증한 테마도 생성한다.

## 🔗 문제 — 제품의 외관 요구가 브랜드색 교체 범위를 넘었다

- 첫 소비 제품인 Smoody Scouter의 코드와 디자인 기록에서 다음이 보였다.
  - 제품 테마 CSS가 UI 패키지의 알약 형태·글래스 표현을 다시 조정하고, 그 조정을 또 다른 CSS가 재조정했다.
  - 제품의 `ProductSelect`는 UI 패키지의 Select를 조합하지만 트리거·팝업·선택·포커스 스타일을 제품에서 다시 정의했다.
  - 제품 CSS가 UI 패키지의 **내부 클래스 구조**에 결합되어 있었고, 포털별로 적용 범위를 나열하고 있었다.
- 모든 CSS 보정의 원인이 디자인 시스템인 것은 아니다. 제품 자체의 디자인 탐색과 누적된 스타일도 원인이다. 하지만 "같은 브랜드색을 모든 제품의 주요 버튼에 강제한다"는 전제가 제품의 실제 요구와 맞지 않는다는 점은 분명했다.

## 🔗 제약

- 기존 소비처(다른 사내 제품과 실험 공간)가 발행된 UI 패키지를 쓰고 있다. 호환성을 깨면 안 된다.
- Scouter는 현재 디자인과 모션을 **그대로 보존**하는 조건으로만 이전할 수 있다. 디자인 변경과 의존성 교체를 같은 작업에서 하면 어느 쪽 회귀인지 알 수 없다.
- 공통 무스타일 래퍼를 새로 만들어 또 하나의 추상화 층을 더하는 것은 원하지 않았다.

## 🔗 선택지

| 선택지                                                                                         | 결과                                                                                                        |
| ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| UI 패키지의 variant·토큰을 늘려 제품 요구를 흡수한다                                           | 제품마다 늘어나는 외관 요구를 중앙이 따라가야 한다. 결합은 그대로다.                                        |
| UI 패키지를 즉시 폐기한다                                                                      | 기존 소비처가 깨진다. 패키지가 제공한 동작(로딩 중 중복 실행 방지, 포커스 유지, 오류 전달)의 가치도 버린다. |
| 토큰·팔레트는 공유하고, 컴포넌트 외관과 조합은 제품이 소유한다. 기존 UI는 호환 범위로 유지한다 | 중앙은 색의 정본과 출처만 책임진다. 제품은 Base UI를 직접 조합한다. 기존 소비처는 단계적으로 이전한다.      |

세 번째를 골랐다. 제품 소유자 요청에 따른 방향 결정이다.

## 🔗 결정 — 소유권을 표로 못 박았다

| 범위                                | 소유와 정책                                                                                                     |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| primitive 색상                      | 토큰 패키지가 값과 출처를 보존한다. 새 팔레트 진입점은 기존 색의 투영이며 값을 새로 만들지 않는다.              |
| 색의 역할·상태·명암 모드            | 제품이 매핑한다. 같은 브랜드색을 모든 제품의 주요 버튼에 강제하지 않는다.                                       |
| 글꼴·간격·반경·그림자               | 필요하면 기존 core를 선택해 쓴다. 공통 의무 규격이 아니다.                                                      |
| 컴포넌트 치수·외관·조합             | 제품이 소유한다. Button · Field · Dialog · Select의 선택적 소스 템플릿을 제공하고, 복사 뒤에는 제품이 수정한다. |
| 기존 UI · semantic · component 토큰 | 호환성 유지 범위. API·값·검증을 보존하고 결함·보안·접근성 수정은 계속한다. 신규 확장은 중단한다.                |
| CLI/MCP                             | 토큰 검색·출처 조회와 호환 UI 문서를 유지한다.                                                                  |

- 새 소비 경로는 색상 CSS 변수만 선언하는 진입점, 접두사 있는 색상 유틸리티만 추가하는 Tailwind 진입점, UI·React 의존 없는 타입 진입점 세 가지다. 표면·컴포넌트·글꼴·레이아웃은 포함하지 않는다.
- 시작 템플릿은 Button · Field · Dialog · Select와 테마를 한 번 복사한다. 자동 변환이나 중앙 업데이트는 하지 않는다. 그것이 "제품 소유"의 뜻이다.

## 🔗 이전 — Scouter에서 실제로 옮긴 순서

1. 제품 레포에 현재 화면과 동작의 기준을 고정했다. 디자인 변경과 의존성 교체를 분리했다.
2. 제품 테마에서 최종 색의 역할을 제품 자체의 CSS 변수로 정리했다. 첫 이전에서는 기존 색상·치수를 보존했다.
3. 이미 단일 진입점이던 `ProductSelect`를 Base UI 직접 조합으로 먼저 옮겼다. 제품에 Base UI를 직접 의존성으로 선언하고, UI 패키지가 쓰던 같은 버전으로 시작했다.
4. 교체한 컨트롤은 제품 클래스와 토큰만 쓰게 했다. 기존 패키지의 내부 구조를 복사해 결합을 유지하지 않았다. 새 부품의 클래스에는 패키지 접두사를 쓰지 않아 공통 포커스 선택자와 분리했다.
5. 값·옵션·disabled·required·name, 폼 제출·검증·라벨, 키보드 선택·Escape·포커스 복귀, 포털의 색·레이어·너비, 긴 문구·모바일·접근성을 확인했다. 기존 제품 검사는 그대로 유지했다.
6. 화면에서 실제 쓰는 Button · Field · Dialog를 순차 이전했다. 패키지가 추가해 주던 동작(로딩 중 중복 실행 방지, 포커스 유지, 오류 전달, 모션 줄이기)은 따로 점검했다.
7. 모든 소비가 제거된 뒤 UI CSS와 SurfaceRoot를 제거하고 UI 패키지 의존성을 뺐다. 토큰 패키지 · CLI와 Base UI는 유지했다.

- 혼용 기간의 함정 하나: 앱 내부 컨테이너의 CSS 변수는 body 포털로 자동 전달되지 않는다. 새 Base UI 팝업의 제품 변수는 `:root` 또는 팝업 자체에서 쓸 수 있어야 한다.

## 🔗 확인 결과

- Scouter의 전체 제품 검사(정적 · 단위/DB · HTTP · 브라우저 흐름 · 디자인 회귀)가 이전 뒤에도 통과했다. 디자인·모션 보존은 디자인 회귀 검사와 Chromium · WebKit 여섯 너비의 캡처 검토로 확인했다.
- 팔레트 진입점은 독립 설치 fixture에서 UI · Base UI · React가 함께 설치되지 않는지, Tailwind 기본 테마와 제품 변수 덮어쓰기가 유지되는지 확인했다.
- 팔레트 단독 진입점과 시작 템플릿은 이 글을 쓰는 시점에 아직 발행 전이다.

## 🔗 남은 제약

- 기존 대비 게이트는 기존 semantic 조합의 검증이다. 팔레트의 임의 조합이나 제품별 Base UI 구현의 접근성은 제품이 검증해야 한다.
- UI 패키지 폐기 일정은 소비처 이전이 끝난 뒤 정한다. Lab과 genui의 잔여 소비도 제거 조건에 포함된다.
- 토큰과 공개 API 수는 구성 규모다. 모든 API가 별개의 완전한 컴포넌트인 것도, 팀 생산성이 그만큼 늘었다는 뜻도 아니다.

## 🔗 면접에서 받을 질문에 대한 답

- **공통 UI를 줄인 이유는 무엇인가?** 중앙이 책임질 수 있는 것은 "값의 정본과 출처"였다. 외관과 조합은 제품마다 달랐고, 그것을 중앙이 따라가면 제품 CSS가 패키지 내부 구조에 결합되는 비용만 커졌다. 공유할 것과 소유할 것을 나누는 편이 두 쪽 모두에 쌌다.
- **그러면 디자인 시스템이 한 일은 무엇인가?** 토큰 생성 · 차이 검사 · 설치 검증 · 발행 게이트 · 문서 조회 경로다. 컴포넌트 개수보다 이 계약들이 남는다.
