## 공통으로 만들었는데, 쓰는 쪽에서 다시 고치고 있었다

사내 디자인 시스템을 만들고 첫 제품에 적용하면서 제품 CSS가 UI 패키지의 내부 클래스를 직접 선택하는 구조를 확인했다. 패키지에서 정한 외관을 제품 테마가 되돌리고, 거기에 다시 스타일을 더하는 식이었다.

어떤 형태였는지 줄여보면 이런 코드다. 실제 파일을 그대로 옮긴 것은 아니고, 제품에서 패키지 내부 구조를 참조하는 상황을 보여주는 예시다.

```css
/* 제품이 패키지 안의 요소 구조까지 알아야 한다. */
.smd-button .smd-button__content {
  gap: 6px;
  letter-spacing: -0.01em;
}
```

이러면 패키지 안의 마크업이나 클래스가 바뀔 때 제품 스타일도 영향을 받는다. 공통 컴포넌트를 쓰고 있는데, 정작 제품에서는 그 내부를 알아야 하는 상황이 됐다.

디자인 시스템을 잘못 사용한 것이라고만 보기는 어려웠다. 제품에서 바꿔야 할 것이 그만큼 많다면, 내가 공통으로 묶어둔 범위도 다시 볼 필요가 있었다.

## 처음에는 어디까지 공통으로 만들었나

토큰, UI 패키지, CLI/MCP 문서 조회 도구를 만들었다. 색상·간격·모션 등의 기준은 토큰 정의에 두고 CSS 변수, 유틸리티, 타입 선언을 생성했다.

생성된 파일을 직접 고치면 다음에 생성할 때 수정이 사라진다. 토큰 정의와 결과도 달라질 수 있으니, 다시 생성한 결과와 저장소의 파일을 비교하는 검사를 넣었다. 정의만 바꾸고 재생성을 잊은 경우도 여기서 확인한다.

패키지를 설치하는 쪽에서도 실제로 쓸 수 있어야 했다. 독립된 환경에 설치해 CSS·모듈·타입을 확인하고, 발행 전에는 브라우저 동작과 시각 회귀, 자동 접근성 검사도 수행했다. 자동 접근성 검사의 범위와 한계는 문서에 남겼다.

### 라이브러리는 같은 화면을 만들어보고 골랐다

Base UI, React Aria Components, Ark UI로 같은 토큰과 컴포넌트를 구현했다. Dialog·Select·Combobox·Menu를 두 가지 테마 표면에서 비교했다.

Base UI 쪽으로 기울어 있기는 했지만, 다른 후보로 바꿀 만한 이유가 있는지도 확인하고 싶었다. 포털에 테마를 전달하는 방식, 추가로 필요한 코드, 상태 속성, 접근성, 번들 크기를 비교했고 Base UI를 채택했다. 비교 조건과 결과는 PoC 보고서로 남겼다.

포털로 띄운 팝업의 테마도 이때 다뤘다. React의 컨텍스트는 전달되지만, 팝업이 앱 컨테이너 밖에 렌더링되면 그 컨테이너의 CSS 변수나 선택자가 그대로 적용되지 않을 수 있다. 팝업에도 같은 표면 정보를 붙이는 규약을 둔 이유다.

문서는 개발자와 에이전트가 설치된 버전의 같은 내용을 볼 수 있도록 CLI와 MCP에서 조회 기반을 공유했다.

## variant를 더 넣으면 해결될까?

처음에는 브랜드색을 토큰으로 바꾸면 여러 제품에서 같은 컴포넌트를 쓸 수 있을 것으로 봤다. 그런데 첫 제품부터 색상 외에 버튼 형태, 크기, 포커스 표현, 팝업 스타일을 바꿔야 했다.

이런 요구를 공통 패키지에 계속 넣을 수도 있다. 다만 그러면 제품마다 바뀌는 외관을 중앙에서 따라가야 한다. 제품은 다음 배포를 기다리고, 당장 필요한 변경은 패키지 내부 클래스에 CSS를 덧대서 처리하게 된다.

그렇다고 모든 스타일 보정의 원인이 디자인 시스템이었던 것은 아니다. 제품 자체의 디자인 탐색과 쌓여 있던 스타일도 있었다. 그래도 외관을 자주 바꿔야 한다는 요구는 분명했으니, 공통으로 관리할 범위를 줄이기로 했다.

기존 패키지를 바로 없앨 수는 없었다. 첫 제품이 이미 발행된 버전에 의존하고 있어서, 지금의 디자인과 동작을 유지하면서 옮겨야 했다.

## 토큰은 공유하고 컴포넌트는 제품에서 관리하기로 했다

제품 소유자와 이야기해서 관리 범위를 다시 나눴다. 색상 값과 출처는 디자인 시스템에 두고, 색을 어떤 역할로 쓸지와 컴포넌트의 외관·조합은 제품에서 정한다.

| 범위                       | 관리 주체와 기준                                              |
| -------------------------- | ------------------------------------------------------------- |
| 기본 색상 값과 출처        | 토큰 패키지에서 공통으로 관리한다.                            |
| 색의 역할과 상태별 표현    | 제품이 필요한 의미와 명암 모드를 정한다.                      |
| 글꼴·간격·반경·그림자      | 기존 토큰을 골라 쓸 수 있지만 모든 제품의 의무 규격은 아니다. |
| 컴포넌트의 외관과 조합     | 제품이 소스를 관리하고 직접 변경한다.                         |
| 기존 UI와 토큰의 소비 경로 | 기존 동작과 호환성을 유지하며 이전한다.                       |

공통 무스타일 래퍼를 새로 만드는 방법도 검토했다. 이번에는 제품에서 헤드리스 UI를 직접 구성하는 쪽을 택했다. 공통 패키지에 층을 하나 더 두기보다 제품이 직접 바꿀 수 있는 범위를 분명하게 정하려고 했다.

### 현재 쓰는 방식과 발행 예정인 방식

첫 적용 제품은 발행된 토큰 JSON에서 팔레트 CSS를 생성해 사용한다. 초기 글을 정리한 시점에 팔레트 전용 진입점과 시작 템플릿은 아직 발행 전이었다.

아래는 그 진입점이 정식 발행된 뒤 사용할 형태의 예시다. 현재 제품에 들어가 있는 경로와는 구분해서 봐야 한다.

```css
/* 팔레트 진입점이 정식 발행된 뒤의 사용 예시 */
@import "@scope/tokens/css/palette";

:root {
  /* 색상 값은 공유하고, 색의 역할은 제품에서 정한다. */
  --app-primary: var(--smd-color-brand-600);
  --app-primary-fg: white;
}
```

제품이 컴포넌트 소스를 가져가면 나중의 결함 수정과 라이브러리 업데이트도 제품에서 해야 한다. 배포를 기다리지 않아도 되는 만큼 유지보수할 코드도 생긴다.

## 기존 디자인을 유지하면서 옮기기

이번 이전에서는 현재 디자인·스타일·모션·사용자 동작을 그대로 유지하는 것을 조건으로 잡았다. 외관을 바꾸는 일과 패키지 의존성을 제거하는 일을 같이 하면, 차이가 생겼을 때 무엇 때문인지 구분하기 어렵다.

진행한 작업은 다음과 같다.

1. 제품이 쓰는 컴포넌트와 필요한 내부 모듈·스타일을 확인했다.
2. 소스를 제품으로 옮기고 import 경로와 제품 소유의 클래스·변수 이름을 정리했다.
3. 포털과 테마 컨텍스트 등 기존 화면의 동작을 유지했다.
4. 공통 UI 패키지의 런타임 의존성을 제거하고 토큰 소비는 남겼다.
5. 소스 대조, 기존 브라우저 검사, 여러 화면 너비의 캡처로 결과를 확인했다.

처음 가져온 코드가 같더라도 이후에는 제품 코드로 관리한다. 외부 패키지의 내부 클래스를 계속 참조하는 것과, 소스를 가져온 뒤 제품에서 변경을 책임지는 것은 다르다.

CSS 변수를 어디에 선언했는지도 확인했다. 앱 컨테이너 안에만 둔 변수는 `body`로 포털된 팝업에서 상속받지 못할 수 있다. 제품 변수의 적용 범위가 팝업까지 닿도록 정리했다.

## 아직 첫 제품에서 확인한 결과다

이전 뒤 기존 제품 검사를 통과했고, 디자인과 모션은 소스 대조·브라우저 검사·캡처로 확인했다. 공통 컴포넌트의 범위를 줄여도 토큰 생성, 결과 비교, 설치 검증, 문서 조회는 그대로 쓸 수 있었다.

이번 제품에서는 외관을 직접 관리하는 쪽을 선택했다. 대신 제품별로 유지보수할 코드가 생겼다.

아직 소비 제품이 하나여서 이 방향이 다음 제품에도 맞을지는 더 봐야 한다. 어디까지 함께 쓰는 게 편한지, 제품에서 따로 관리할 비용은 어느 정도인지 다음 적용에서 확인해보려고 한다.
