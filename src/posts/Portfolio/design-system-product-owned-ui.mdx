# 🎨 공통화는 늘리는 것만큼 줄이는 때를 아는 일일까?

---

## 🔗 들어가며

### ✨ 제품 CSS 에서 `.smd-button__content` 를 만났다

- 사내 디자인 시스템을 만들고 몇 달 뒤, 첫 소비 제품의 스타일 파일을 열어 보다가 이런 선택자를 만났다.

```css
/* 제품 레포의 theme.css */
.smd-button .smd-button__content {
  gap: 6px;
  letter-spacing: -0.01em;
}
```

- `smd-` 는 내가 만든 UI 패키지의 접두사다. 제품이 패키지의 **내부 구조**를 알고 거기에 CSS 를 덧대고 있었다. 그 아래로는 패키지의 알약 모양 버튼을 제품 테마가 다시 조정하고, 그걸 또 다른 CSS 가 재조정하는 층이 세 겹쯤 쌓여 있었다.

> 이걸 "제품이 디자인 시스템을 잘못 썼다" 로 읽을 수도 있다. 그런데 나는 반대로 읽었다. **공통 UI 의 범위를 내가 잘못 잡았다.**

- 이번 글은 디자인 토큰 · UI 패키지 · CLI/MCP 로 이루어진 디자인 시스템을 만든 뒤, **컴포넌트 외관을 제품에게 돌려주고 토큰만 공통으로 남기기**로 한 결정의 기록이다.

---

## 🔗 먼저 만든 것 — 정본과 생성물 사이의 계약

### 🧩 토큰은 생성한다, 손으로 고치지 않는다

- 디자인 시스템의 중심은 토큰 JSON 이다. 여기서 CSS 변수 · Tailwind 프리셋 · JS 상수 · 타입 선언을 **생성**한다. 토큰마다 어디서 왔는지 출처를 남긴다.

- 생성물을 누군가 손으로 고치면 정본과 갈라진다. 그래서 빌드 전에 "다시 생성해도 같은가" 를 검사하는 게이트를 뒀다.

```js
// scripts/check-drift.mjs — 생성물을 스냅샷하고, 다시 생성한 뒤, 비교한다
const before = snapshot(["tokens", "css", "tailwind", "ts"]);
execFileSync("npm", ["run", "build", "-w", "@scope/tokens"]);
assert.deepEqual(snapshot([...]), before, "Generated tokens were stale.");
```

- 손으로 고친 생성물도, 정본만 바꾸고 재생성을 잊은 커밋도 여기서 떨어진다. 이 한 줄이 "정본은 JSON 이다" 를 CI 가 보증하게 만든다.

### 🧪 라이브러리는 반증을 시도해 보고 고른다

- UI 패키지의 기반으로 Base UI · React Aria Components · Ark UI 를 **같은 토큰 위에서 똑같이** 구현해 비교했다. Dialog · Select · Combobox · Menu 를 두 가지 surface 로.

  프레이밍은 "Base UI 채택 결정에 대한 반증 시도" 였다. 이미 기울어 있던 결정을 확인하는 PoC 가 아니라, 뒤집을 이유를 찾는 PoC.

- 본 것은 포털 × surface 주입, 상태 data 속성 커버리지, 래퍼 두께, Combobox 필터링 배선, axe 감사, 구현 중 실제로 겪은 사고, 번들이다. 반증은 실패했고 Base UI 로 확정했다.

### 🧭 포털로 나간 팝업이 테마를 잃지 않게

- 다크 surface 안에서 연 Select 의 팝업이 `document.body` 로 포털되면 라이트로 뜨는 문제가 있다. React Context 와 DOM 의 `data-surface` 를 **하나의 API** 로 묶어서 풀었다.

```tsx
const SurfaceCtx = createContext<Surface>("marketing");

export function SurfaceRoot({ surface, children, ...props }: SurfaceRootProps) {
  return (
    <SurfaceCtx.Provider value={surface}>
      <div data-surface={surface} {...props}>
        {children}
      </div>
    </SurfaceCtx.Provider>
  );
}

// 패키지 안의 모든 Popup 래퍼는 Context 값을 자기 data-surface 로 다시 찍는다
function Popup(props) {
  const surface = useContext(SurfaceCtx);
  return <BaseUI.Popup data-surface={surface} {...props} />;
}
```

- 사용처는 `data-surface` 를 직접 쓰지 않는다. Context 는 product 인데 DOM 은 marketing 인 불일치 사고를 막기 위해서다. PoC 에서 세 라이브러리 모두에서 성립함을 확인한 규약이다.

### 📦 발행 게이트

- 독립 설치 fixture 가 실제 tarball 을 소비해 CSS · Tailwind · ESM · 타입이 설치되는지 본다. 세 브라우저의 계약 검사, 시각 회귀, axe 자동 접근성 · 대비 검사를 통과해야 사내 패키지 저장소로 나간다. 자동 검사가 전체 접근성 인증을 뜻하진 않는다는 문장은 README 에 그대로 적어 뒀다.

- CLI 와 stdio MCP 는 같은 manifest 와 조회 함수를 공유한다. 개발자는 CLI 로, 에이전트는 MCP 로 **설치한 버전**의 문서를 본다.

## 🔗 문제 — 외관 요구가 브랜드색 교체 범위를 넘었다

### 🚫 "브랜드색만 바꾸면 되겠지" 가 틀렸다

- UI 패키지를 설계할 때의 전제는 이랬다. 제품마다 다른 건 브랜드색 정도고, 그건 토큰으로 바꾸면 된다. 버튼 모양 · 높이 · 포커스 링은 공통이어도 된다.

- 첫 소비 제품은 그 전제를 비껴갔다.

  - 제품의 `ProductSelect` 는 패키지의 Select 를 조합하지만, 트리거 · 팝업 · 선택 · 포커스 스타일을 **전부** 다시 정의했다.
  - 제품 테마가 패키지의 알약 형태와 글래스 표현을 되돌리고, 그 위에 또 조정이 쌓였다.
  - 그 조정들이 포털별로 적용 범위를 나열하며 패키지 내부 클래스에 결합됐다.

- 모든 CSS 보정의 원인이 디자인 시스템인 건 아니다. 제품 자체의 디자인 탐색과 누적된 스타일도 있다. 하지만 **"같은 브랜드색을 모든 제품의 주요 버튼에 강제한다"** 는 전제가 제품의 실제 요구와 안 맞는다는 건 분명했다.

### 🤔 그럼 variant 를 더 늘리면 되지 않나

- 첫 반응은 그랬다. 패키지에 variant 와 토큰을 더 넣어 제품 요구를 흡수하자.

  그런데 그건 제품마다 늘어나는 외관 요구를 **중앙이 계속 따라가는** 길이다. 결합은 그대로고, 패키지는 비대해진다.

- 반대로 패키지를 즉시 폐기하는 것도 답이 아니었다. 다른 소비처가 발행된 버전을 쓰고 있었고, 패키지가 제공하던 **동작**(로딩 중 중복 실행 방지, 포커스 유지, 오류 전달)은 외관과 별개로 가치가 있었다.

## 🔗 결정 — 토큰은 공유하고, 외관은 제품이 소유한다

### 💡 소유권을 표로 못 박았다

- 제품 소유자와 이야기해 방향을 바꿨다. 무엇을 중앙이 책임지고 무엇을 제품이 가져가는지를 표로 적었다.

| 범위                                | 소유                                                                           |
| ----------------------------------- | ------------------------------------------------------------------------------ |
| primitive 색상 (값 · 출처)          | 토큰 패키지. 새 팔레트 진입점은 기존 색의 투영이지 새 값이 아니다              |
| 색의 역할 · 상태 · 명암 모드        | 제품. 같은 브랜드색을 모든 제품의 주요 버튼에 강제하지 않는다                  |
| 글꼴 · 간격 · 반경 · 그림자         | 필요하면 기존 core 를 골라 쓴다. 공통 의무 규격이 아니다                       |
| 컴포넌트 치수 · 외관 · 조합         | 제품. Button · Field · Dialog · Select 의 소스 템플릿을 한 번 복사해 준다      |
| 기존 UI · semantic · component 토큰 | 호환성 유지. API · 값 · 검증은 보존하고 결함 수정만 계속한다. 신규 확장은 중단 |

- 새 소비 경로는 세 가지뿐이다. 색상 CSS 변수만 선언하는 진입점, 접두사 있는 색상 유틸리티만 추가하는 Tailwind 진입점, UI · React 의존이 없는 타입 진입점. 표면 · 컴포넌트 · 글꼴 · 레이아웃은 **안 들어 있다**.

```css
/* 제품 전역 CSS — 색만 받는다 */
@import "@scope/tokens/css/palette";

:root {
  /* 색의 "역할" 은 제품이 정한다 */
  --app-primary: var(--smd-brand-600);
  --app-primary-fg: white;
}
```

- 시작 템플릿은 **복사 한 번**이다. 자동 변환도, 중앙 업데이트도 없다. 그게 "제품 소유" 의 뜻이다.

### 🤔 공통 무스타일 래퍼를 새로 만들지 않은 이유

- "그럼 headless 래퍼를 공통으로 두고 스타일만 제품이" 라는 안도 있었다. 하지만 그건 추상화 층을 하나 더 쌓는 일이다. 제품은 Base UI 를 **직접** 쓰면 된다. 제품에 Base UI 를 강제하지도 않는다.

## 🔗 이전 — 디자인 변경과 의존성 교체를 같은 PR 에 넣지 않는다

### ⬇️ 순서

- 첫 소비 제품은 현재 디자인과 모션을 **그대로 보존**하는 조건으로만 이전할 수 있었다. 그래서 순서를 이렇게 잡았다.

1. 제품 레포에 지금 화면과 동작의 기준을 고정한다. 디자인 변경과 의존성 교체를 섞지 않는다.
2. 제품 테마에서 최종 색의 역할을 제품 변수로 정리한다. 첫 이전에서는 색상 · 치수를 그대로 둔다.
3. 이미 단일 진입점이던 `ProductSelect` 하나를 Base UI 직접 조합으로 먼저 옮긴다.
4. 교체한 컨트롤은 제품 클래스와 토큰만 쓴다. 패키지 내부 구조를 복사해 결합을 이어 가지 않는다. 새 클래스에는 패키지 접두사를 쓰지 않아 공통 포커스 선택자와 분리한다.
5. 값 · 옵션 · disabled · required · name, 폼 제출 · 검증 · 라벨, 키보드 · Escape · 포커스 복귀, 포털의 색 · 레이어 · 너비, 긴 문구 · 모바일 · 접근성을 확인한다.
6. 화면에서 실제 쓰는 Button · Field · Dialog 를 순차 이전한다. 패키지가 덤으로 주던 동작은 따로 점검한다.
7. 모든 소비가 빠진 뒤 UI CSS 와 SurfaceRoot 를 제거하고 UI 패키지 의존성을 뺀다. 토큰과 CLI 는 그대로 둔다.

### 🚫 혼용 기간의 함정 하나

- 앱 안쪽 컨테이너에 선언한 CSS 변수는 **body 로 포털된 팝업에 전달되지 않는다**. 새 Base UI 팝업이 쓰는 제품 변수는 `:root` 에 두거나 팝업 자체에서 다시 선언해야 했다.

```css
/* ❌ 앱 컨테이너에만 두면 body 포털 팝업이 못 본다 */
#app-root {
  --app-popup-bg: #111;
}

/* ✅ 포털도 보는 자리 */
:root {
  --app-popup-bg: #111;
}
```

- 이전 뒤 제품의 전체 검사(정적 · 단위/DB · HTTP · 브라우저 흐름 · 디자인 회귀)가 그대로 통과했고, 디자인 · 모션 보존은 디자인 회귀 검사와 여러 너비의 캡처 검토로 확인했다.

## 🔗 남는 교훈

### 💡 중앙이 책임질 수 있는 건 "값의 정본" 이었다

- 외관과 조합은 제품마다 달랐고, 그걸 중앙이 따라가면 제품 CSS 가 패키지 내부에 결합되는 비용만 커졌다. 공유할 것과 소유할 것을 나누는 편이 두 쪽 모두에 쌌다.

- 그러면 디자인 시스템이 한 일은 뭐냐고 물으면, 이렇게 답하게 됐다.

> 토큰 생성 · 차이 검사 · 설치 검증 · 발행 게이트 · 문서 조회 경로.
> 컴포넌트 개수보다 이 **계약들**이 남는다.

- 팔레트 단독 진입점과 시작 템플릿은 이 글을 쓰는 시점에 아직 발행 전이다. UI 패키지의 폐기 일정은 소비처 이전이 끝난 뒤에 정한다.

### 🤔 공통 UI 가 비대해지고 있다면

- 디자인 시스템이나 공통 컴포넌트 패키지를 운영 중이라면, 다음 질문을 던져보면 좋겠다.

  - 소비 제품의 CSS 가 패키지의 **내부 클래스**를 선택하고 있는가?
  - 제품의 외관 요구가 **토큰 값 교체**로 끝나는가, 컴포넌트 구조까지 바꾸는가?
  - 패키지가 주는 가치가 **외관**인가 **동작**인가?

- 첫 질문에 "그렇다" 가 나온다면, variant 를 늘리기 전에 그 컴포넌트를 제품에게 돌려보내는 선택지를 한 번 놓고 보자. 공통화를 줄이는 것도 설계다.

  😁 이 결정 뒤로 "이걸 공통으로 뺄까" 를 고민할 때 "그럼 이건 누가 소유하지" 를 먼저 묻게 됐다. 답이 "중앙" 이 아니면 안 빼는 쪽으로 기울었다.
