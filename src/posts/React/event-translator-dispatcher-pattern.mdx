# 🧩 이벤트와 상태, 한 함수 안에 같이 있어도 괜찮을까?

---

## 🔗 들어가며

### ✨ 핸들러 한 줄을 고치려는데 reset 정책까지 봐야 했다

- 최근 SSE 기반의 실시간 채팅 화면 코드를 한참 들여다보고 있었다.

  처음엔 단순했다. 백엔드가 보내는 이벤트 한 종류에 핸들러 한 개. **1:1 매핑**이니까 자연스러워 보였다.

- 그런데 시간이 지나면서 한 가지 패턴이 반복해서 발목을 잡았다.

> 핸들러 한 줄을 고치려고 들어갔는데, 결국 스토어의 `reset()` 정책까지 같이 봐야 한다.

- 이번 포스트에서는 80개 가까이 늘어난 SSE 이벤트 핸들러를 **Translator + Dispatcher** 구조로 분리하며 겪은 시행착오와 회고를 정리해보고자 한다.

---

## 🔗 처음의 구조 — 핸들러 하나가 너무 많은 일을 한다

### 🚫 비대해진 핸들러 파일

- 리팩터링 이전의 핸들러 파일은 한 1800줄쯤 됐다. 대략 이런 모양이었다.

```ts
// sse-event-handlers.ts (약 1800줄, 핸들러 80여 개)
const handlers = {
  "run.started": (event, ctx) => {
    // (1) 이벤트의 의미 해석
    const { runId, sessionId } = event.payload;

    // (2) 스토어 직접 mutation
    runStore.setCurrentRunId(runId);
    if (sessionId) runStore.setCurrentSessionId(sessionId);
    runStore.setRunStatus("running");

    // (3) lifecycle 가드
    if (ctx.ownerKey !== streamStore.ownerKey) return;

    // (4) side-effect
    messageStore.appendPlaceholder(runId);
  },
  // ... 80개 가까이
};
```

- 핸들러 함수 하나 안에 들어있는 책임이 너무 많다.
  - **이벤트 의미 해석** — `event.payload` 에서 무엇을 꺼낼지
  - **스토어 직접 mutation** — 어느 스토어의 어느 액션을 부를지
  - **lifecycle 가드** — owner 가 일치하는지, mount 직후인지
  - **side-effect** — placeholder 추가 같은 외부 작용

### 🤔 그러면 한 함수가 많은 일을 하면 안 되나?

- 안 된다기보다, **변경이 들어오는 축이 너무 많아진다**는 게 진짜 문제였다.

  백엔드가 이벤트 이름을 한 번 바꾸면 핸들러 80개 중 어디가 영향받는지 추적해야 한다.

  스토어의 `reset()` 정책을 한 번 바꾸면 또 80개를 다시 본다.

- 결정적으로, 어느 날 다음과 같은 결함이 한 번 터졌다.

  - 어떤 mount effect 안에서 `setCurrentSessionId(...)` 를 호출한 뒤, 곧장 `runStore.reset()` 이 호출된다.
  - `reset()` 의 preserve 정책에 `currentSessionId` 가 포함되어 있지 않다 보니, 방금 박은 값이 **즉시 wipe** 된다.
  - 결과적으로 첫 mount 직후 화면에서 사용자 입력 카드가 어떤 세션에 속한 응답인지 판별하지 못해 disabled 상태로 박힌다.

- 코드 수정 자체는 별거 없었다. effect 안의 호출 순서를 바꾸고, 스키마의 optional 가드 한 줄 추가하면 끝.

  ❌ 그런데 **진단이 어려웠던 이유**는 코드 한 줄의 결함이 아니라 **책임 누설**이었다.

> 핸들러가 store 의 reset 정책을 알아야 정상 동작하는 상태.  
> 외부 lifecycle 의 내부 구현을 호출자가 알아야 코드가 굴러간다는 뜻이다.

- 이게 바로 **wire 어휘**와 **도메인 어휘**가 한 함수 안에 섞여 있다는 신호다.

## 🔗 한 가지 통찰 — 이벤트는 그냥 IO 다

### 💡 wire 어휘 vs 도메인 어휘

- 이번 리팩터의 출발점이 된 한 문장이 있다.

> **이벤트는 IO 다. event vocabulary 가 BE 측 결정으로 변해도, FE 의 핵심은 invariant 여야 한다.**

- 풀어보면 이런 얘기다.

  - **Wire 어휘** — `run.started`, `text.delta`, `tool_use.confirmation`, … 이건 백엔드의 결정이다. 프론트가 통제할 수 없다.
  - **도메인 어휘** — `RunBegan`, `AssistantTextChunk`, `ToolConfirmationOpened`, … 이건 프론트의 결정이다. 사용자에게 어떤 의미인지를 표현한다.

### 🤔 굳이 이걸 둘로 나눠야 하나?

- 같은 의미 (예: "run 이 시작됨") 가 wire 단에서 `run.started` 와 `run.snapshot` 두 곳에 분산되어 있다고 해보자.

  도메인 코드는 둘 다를 알 필요가 없다. **`RunBegan` 하나면 충분**하다.

- 뒤집어 말하면,
  - 백엔드가 `run.started` 를 `run.begin` 으로 rename 해도 → 프론트의 core 는 영향받지 않아야 한다.
  - 새 이벤트가 추가되어도 → 도메인 의미가 같다면 store 의 action 목록은 안 늘어나야 한다.

> 즉, **wire 의 변동성을 한 층 안에 가두는 것**이 목표였다.

## 🔗 네 가지 원칙

### 1️⃣ Wire 어휘와 도메인 어휘를 분리한다

- 핸들러 파일이 직접 store action 을 호출하지 말 것.
- 그 사이에 **변환층**을 둔다.

### 2️⃣ Event → Intent 변환은 thin / pure / 1:1

- 변환층은 어떤 store / hook / lifecycle 도 모른다.
- 입력은 wire event, 출력은 intent (또는 intent 배열).
- 같은 입력에는 항상 같은 출력 → idempotent.

### 3️⃣ Core state machine 은 wire 어휘를 모른다

- Store action 의 시그니처에 wire event 가 등장하지 않는다.
- 새 wire event 가 추가되어도 store 의 action 목록은 안 늘어난다.
- **진짜 새 의미**일 때만 새 intent 가 추가된다.

### 4️⃣ Lifecycle 은 store 의 책임이지 handler 의 책임이 아니다

- 핸들러가 `reset()` 직후의 상태를 알아야 정상 동작한다면 그건 책임 누설이다.
- Store 의 reset 은 "어떤 필드를 preserve / wipe 할지" 를 자체 정책으로 명시한다.
- 핸들러는 reset 의 내부를 몰라도 호출 가능해야 한다.

## 🔗 새 구조 — Translator → Dispatcher → Store action

### ⬇️ 데이터 흐름 비교

- **리팩터 이전**

```text
SSE wire ──→ parse ──→ handler (~80개, ~1800줄) ──→ 5+ store 직접 mutation
                          │                              │
                          ├─ 이벤트 의미 해석                ├─ Lifecycle 가드
                          ├─ store mutation 직접            ├─ owner 가드
                          ├─ runStatus 전이                 ├─ message commit
                          └─ side-effect                   └─ pending 정리
```

- **리팩터 이후**

```text
SSE wire ──→ parse ──→ Translator ──→ Intent dispatcher ──→ Store actions
                       (얇은 매핑)      (intent → store 라우팅)   (도메인 어휘)
                       │                │                       │
                       wire 변경 흡수     store lifecycle 모름       reset/preserve 자체 책임
                       event 변경 시      intent 의 의미만 알고        외부 lifecycle 과 정합
                       여기만 갱신        어느 store action 호출       되는 단일 출처
```

### 💡 각 층이 모르는 것

- **Translator** — store 가 있다는 걸 모른다. wire event 를 받아 intent 객체만 돌려준다. **순수 함수**.
- **Dispatcher** — wire event 가 있다는 걸 모른다. intent 를 받아 store action 만 호출한다.
- **Store action** — 도메인 어휘만 받는다. reset / preserve / owner 가드는 자체 책임.

> 분리의 본질은 레이어 수를 늘리는 게 아니라, **각 레이어가 모르는 것을 명확히 만드는 일**이다.

### ⬇️ 코드로 보면

- **리팩터 이전**

```ts
// handler 가 wire 객체를 받아 store 를 직접 mutate
"reasoning.delta": (event, ctx) => {
  const text = event.payload.text;
  if (!text) return;
  streamStore.appendReasoningDelta(ctx.ownerKey, text);
},
```

- **리팩터 이후**

```ts
// translator — wire → intent, 순수 함수
export function translateReasoningDelta(
  event: ReasoningDeltaEvent,
): ReasoningIntent | null {
  const text = event.payload.text;
  if (!text) return null;
  return { kind: "delta", text };
}

// dispatcher — intent → store action
export function dispatchReasoningIntent(
  intent: ReasoningIntent,
  deps: { streamStore: StreamStoreDeps },
  ctx: EventContext,
) {
  if (intent.kind === "delta") {
    deps.streamStore.appendReasoningDelta(ctx.ownerKey, intent.text);
  }
}

// handler 본체 — translator + dispatcher 위임만
"reasoning.delta": (event, ctx) => {
  const intent = translateReasoningDelta(event);
  if (intent) dispatchReasoningIntent(intent, deps, ctx);
},
```

### 🤔 이렇게 나누면 정말 좋은 게 뭔데?

- 변경의 영향 범위가 **레이어 한 층에 갇힌다**.

| 변경 종류 | 영향 받는 층 |
|---|---|
| BE 가 `run.started` 를 `run.begin` 으로 rename | Translator 한 줄. core 무영향 |
| BE 가 `human_input.requested.kind` 에 새 값 추가 | Translator 의 narrowing 분기. core 무영향 |
| BE 가 새 event 추가 | Translator 에 항목 추가. 의미가 진짜 새로우면 그때만 intent + store action 추가 |
| FE store 의 reset 정책 변경 | Store 자체. handler 무영향 |
| 새 surface (mobile / embed) 추가 | core 그대로 재사용 |

- 이전에는 한 줄을 바꿀 때마다 lifecycle 까지 거슬러 올라가는 git blame 사파리를 떠나야 했다.

  ✅ 지금은 영향이 한 층에 갇힌다.

## 🔗 단계적 마이그레이션 — 한 번에 다 갈 수는 없다

### 🚫 한 PR 로 갈아엎으려는 욕심

- 이걸 한 방에 다 갈아엎겠다고 덤볐다가는 streaming hot path 의 정교한 튜닝 (leaf 격리, drain pacer, owner 가드) 이 한꺼번에 무너진다.

- 그래서 다음 단계로 분할했다.

### Phase 1 — Store action invariant 의 명문화

- 가장 비용이 작고 효과가 큰 단계.

  - 4 개 store 의 `reset()` / `clear()` 위에 **preserve 정책 JSDoc 블록**을 부착.
  - 어떤 필드를 preserve / wipe 하는지, **왜** 그러는지, 외부 lifecycle 가정이 한 자리에 명시.

- 그리고 각 mutate action 에는 다음 4 항을 JSDoc 으로 부착.
  - 호출자
  - 사후조건
  - lifecycle (reset 영향)
  - 호출 순서 제약

- JSDoc 만 추가하니 코드 동작은 안 바뀐다 → **회귀 위험 0**.
- 그런데도 다음 단계의 리팩터에서 "이 필드는 preserve 인가 wipe 인가" 를 확정할 단일 출처가 생긴다.

> 💡 리팩터는 항상 **현 상태의 invariant 를 명문화하는 단계**가 선행되어야 한다.  
> "지금 이게 왜 이렇게 되어있지?" 를 답하지 못하면, 바꿔도 되는지 판단할 근거가 없다.

### Phase 2 — Store 단위 테스트 + Run state machine 추출

- vitest 를 활성화해 store invariant spec 30+ 확보.
- run lifecycle 의 transition 을 **순수 함수**(`applyRunLifecycle`)로 추출, `RunIntent` 라는 discriminated union 도입.

```ts
export type RunIntent =
  | { kind: "begin"; runId: string; sessionId?: string }
  | { kind: "completed"; runId: string }
  | { kind: "errored"; runId: string }
  | { kind: "cancelRequested"; runId?: string }
  | { kind: "cancelAcked"; runId?: string }
  | { kind: "enterReasoning" }
  | { kind: "enterStreaming" }
  | { kind: "enterToolCalling" };

export function applyRunLifecycle(
  state: RunLifecycleState,
  intent: RunIntent,
): RunLifecycleState;
```

- 순수 함수로 빼두면 store 의 action 은 **transition 자체를 위임**하는 얇은 래퍼가 된다.

  ✅ `same-state identity` (입력 state 와 동일하면 같은 참조 반환) 까지 보장하면, delta storm 같은 hot path 에서 zustand listener 의 불필요한 순회도 차단할 수 있다.

### Phase 3 — Handler → Translator + Dispatcher

- 본 리팩터의 본체.
- 80개 가까운 handler 중 store mutation 을 보유한 36개를 모두 두 단계로 분리.
  - 도메인별 translator 모듈 (run / reasoning / text / tool-use / human-input / …) — wire → intent
  - intent dispatcher — intent → store action

- PR 단위는 **도메인 하나당 하나** 로 쪼갰다. 같이 옮길수록 회귀 위험이 곱해진다.

- 종결 시점에 다음 성과가 나왔다.
  - handler 파일 1800+ 줄 → 약 800줄 (60% 감소)
  - handler 본체의 store mutation 잔존 = 1 건 (history merge dedup 계산용 특수 케이스)
  - handler 의 SDK import 가 `SseEvent` type 단일로 축소 — wire 어휘가 모두 translator 표면에 한정

### Phase 4 — runtime SDK 로 승격

- 분리하고 보니 어느 순간 깨달았다.

  > Translator + dispatcher + state machine 까지 한 번 분리하고 나니, 이게 더 이상 **특정 앱에 종속된 코드**가 아니라는 게 드러났다.

- 셋 다 의존성이 한 방향으로만 흐른다.
  - 어떤 store 가 있는지 모르는 translator
  - 어떤 wire 가 있는지 모르는 dispatcher (의존성을 DI 로 받음)
  - framework-agnostic 한 순수 state machine

- 그래서 runtime 코어로 SDK 에 합류시켰다.

  ✅ 어떤 surface (web / mobile / embed widget) 가 와도 자기 store interface 만 wrap 하면 그대로 재사용 가능.

```ts
// surface 측 (예시)
const dispatcher = createIntentDispatcher(deps);
//                                        ^^^^ 자기 zustand store 를 wrap 한 deps
```

## 🔗 리팩터링이 끝난 자리에서 본 것

### 💡 가장 크게 바뀐 것 — 변경 영향 범위가 측정 가능해졌다

- BE 가 wire event 를 rename 한다 → translator 한 줄만 보면 된다.
- store 의 reset 정책을 바꾼다 → JSDoc 의 preserve 목록을 갱신한다.
- 새 surface 를 붙인다 → dispatcher 의 deps interface 만 구현한다.

> 좋은 분리는 **레이어를 세 개로 늘리는 게 아니라**, 각 레이어가 모르는 것을 명확히 만드는 일이다.  
> Translator 는 store 를 모른다. Dispatcher 는 wire 를 모른다. Store 는 lifecycle 의 외부 호출자를 모른다.  
> "모른다" 가 보장되어야 비로소 한 층의 변경이 다른 층으로 전염되지 않는다.

### 🤔 비슷한 구조에서 똑같이 고민 중인 사람에게

- 만약 SSE 기반 / 실시간 이벤트 기반 아키텍처에서 핸들러가 비대해지고 있다면, 다음 질문을 던져보면 좋겠다.

  - 핸들러가 store 의 reset 정책을 알아야 동작하는가?
  - 같은 도메인 의미가 두 개 이상의 wire event 에 분산되어 있는가?
  - BE 가 event 를 rename 했을 때, 영향 범위가 한 줄로 좁혀지는가?

- 셋 중 하나라도 "그렇다" 라면, **Translator + Dispatcher** 같은 얇은 분리만으로도 변경 비용이 크게 떨어질 것이다.

  😁 본인은 이번 리팩터 이후로 핸들러 파일을 열 때마다 "아 이게 wire 일인지 도메인 일인지" 부터 분간하는 버릇이 생겼다. 좋은 신호 같다.
